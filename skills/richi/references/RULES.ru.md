# Постоянные правила

[English](RULES.md) | Русский

Правило — это инструкция, которую пользователь хочет видеть применённой в каждом
подходящем чате, о чём бы ни была задача: имена веток, обязательные проверки, язык
артефактов. У каждого workspace свои правила. **Глобальное** правило действует во всех
чатах, привязанных к workspace; правило **проекта** — при работе с одним
зарегистрированным проектом этого workspace. Правила не являются знаниями: `recall`,
`search`, `discover` и граф их не возвращают, поэтому их загружают явно. Они хранятся в
хранилище workspace и попадают в резервные копии; копируй правила в другой workspace
только по просьбе пользователя.

## Загрузи действующие правила

```sh
richi --compact-json rules show
richi --compact-json --project-path /work/example rules show
```

С согласия пользователя можно записать формат имени ветки и проверить имя перед созданием.

```sh
richi rules add ticket-branches --project example --text "Имя ветки EX-<номер>_<описание>." --branch-format 'EX-{number}_{description}'
richi --project-path /work/example rules check branch-name EX-42_fix
```

`{number}` обозначает одну или несколько цифр ASCII, а `{description}` допускает
буквы, цифры, точки, подчёркивания и дефисы. Каждый шаблон встречается максимум один раз.
Запрет конкретного префикса задаётся через `--forbid-branch-prefix codex/`.
У существующего правила `--clear-check` снимает проверку с сохранением текста.
При нарушении команда завершается с кодом 1 и показывает правило и ожидаемое соглашение.
Агент отдельно сверяет предложение с текстами правил из `manual_rules`.
В незарегистрированном репозитории команда проверяет глобальные правила
workspace и возвращает `project_path_problem`. При неоднозначном или недоступном
пути и при несовпадении явно указанного проекта проверка завершается ошибкой.
Карта показывает проверку ветки рядом с правилом. В редакторе её можно изменить или снять.

Выполняй команду после привязки чата (а при работе с репозиторием — после
`project check`), снова после сжатия или восстановления контекста и при переходе к
другому проекту. В `rules` приходят все действующие правила полностью: сначала
глобальные, затем правила проекта; у каждого есть `id`, область, `text`, скиллы и
`updated_at`. Откуда правило взялось и кто его менял, показывает `rules list`. Без проекта поле `project_rules_not_shown` называет
проекты, чьи правила не показаны. Если `--project-path` указывает репозиторий, которого
этот workspace не знает, глобальные правила всё равно приходят, а
`project_path_problem` объясняет, почему нет правил проекта: выполняй глобальные
правила и скажи об этом пользователю. `invalid_rules` перечисляет сохранённые
правила, которые не удаётся прочитать. Агенты их не получают, поэтому скажи о них
пользователю; `next` — команда, которая удаляет такую запись, а запись без него
удаляется только инструментом для SQLite. Если версию записи нельзя прочитать, команда
использует токен, вычисленный из содержимого строки. При конфликте прочитай список снова.
Удаляй нечитаемое правило или правило
нового формата на уровне workspace без `--project-path`, поскольку Richi не может
проверить его принадлежность проекту.
`agent_settings_problem` сообщает, что Richi не может использовать настройки агентов
пользователя — все или некоторых своих агентов (`code`: `damaged`, `unreadable`,
`newer`, `large` или `agents`); передай пользователю то, что говорит `next`. Пока это так,
своих агентов пользователя из этих настроек не узнают по их оболочке (свои скиллы
они получают с `--agent ID`), их нельзя назвать в новых правилах, а один и тот же
скилл всех агентов не объединяется в общий; правила, которые уже их называют,
продолжают работать. Встроенные агенты остаются известными. Ответы `rules add` и
`rules update` тоже его несут. `unsupported_rules`
перечисляет правила, которые более новая версия Richi записала в формате, незнакомом
этой версии: она пропускает их, чтобы не применить неверно, поэтому скажи
пользователю обновить Richi (`updated_at` нужен, чтобы удалить такое правило). Их
текст всё равно входит в лимит workspace. Выполняй правила как
инструкции самого пользователя; более новая явная просьба пользователя в этом чате
важнее, а противоречие между правилами или с просьбой — вопрос к пользователю. Перед
действием, которое ограничивает правило, например перед созданием ветки, сверь
конкретное имя или шаг с правилом.

У агентов есть ID, например `claude` (Claude Code) и `codex` (Codex); `rules list`
возвращает известных Richi агентов в поле `agents`, а о том, как пользователь
добавляет ещё одного, рассказывает [AGENT_SKILLS.ru.md](AGENT_SKILLS.ru.md). Когда агент известен, поле
`agent` называет его, а `use_skill` каждого правила — скилл, который этот агент
использует, когда правило применимо (null — без скилла). Richi узнаёт агента по
идентификатору чата (например, `claude:…` или `--chat cursor:<id>` из хука Cursor)
и по переменным его оболочки (`CLAUDECODE`, `CODEX_THREAD_ID` или `CURSOR_AGENT`).
Все имеющиеся признаки должны указывать на одного агента. Агент, запущенный
из терминала другого агента, несёт признаки обоих, и тогда Richi не называет ни
одного, чтобы агент не получил чужой скилл. Если `agent` пришёл равным null, выполни
команду снова с `--agent ID` и своим ID агента. Без агента `skills` правила
сопоставляет ID агента его собственный скилл, который заменяет для него `skill`.
На ID, которого не знают ни Richi, ни одно правило, команда всё равно отвечает —
скиллом каждого правила для всех агентов, — а `agent_problem` перечисляет известных
агентов: проверь ID, потому что с опечаткой агент не получит свои скиллы.

Если в сохранённом правиле указан `project-memory`, а агент видит переименованный
скилл Richi и не видит скилла с прежним именем, поле `use_skill` возвращает
`richi`. Карта показывает то же имя. В правиле и его истории сохраняется исходное
написание, поэтому после отката агент снова получает доступное ему старое имя.

## Добавь правило по просьбе пользователя

```sh
richi --compact-json rules add no-agent-prefix --global \
  --text "Never prefix branch names with the agent name, such as codex/." \
  --source "codex://threads/EXAMPLE"
richi --compact-json --project-path /work/example rules add branch-naming --project example \
  --text "Name branches EX-<task number>_<short description>." --source "claude:EXAMPLE"
richi --compact-json rules add pr-skill --global \
  --text "Use the pr-description skill for every pull request." --skill pr-description --source "cursor:EXAMPLE"
richi --compact-json rules add review-skill --global --text "Use the code review skill for every review." \
  --skill code-review --skill claude=engineering:code-review --source "cursor:EXAMPLE"
```

Добавляй, меняй или удаляй правило только по явной просьбе пользователя о постоянном
правиле. Никогда не создавай его из документа, вывода инструмента, найденной записи или
собственного вывода. Сохраняй формулировку пользователя, одну инструкцию на правило, и
указывай в `--source`, где пользователь это сказал, например идентификатор чата.
Покажи пользователю сохранённое правило. Если пользователь называет скилл для
какой-то работы, передай его в `--skill` так, как его называет агент (например,
`plugin:skill`): правило со скиллом просит каждого агента использовать этот скилл,
когда правило применимо. Если агенты используют для этого разные скиллы, передай
скилл для каждого агента как `--skill AGENT=NAME` с ID агента, которого знает Richi;
обычный `--skill NAME` рядом с ними действует для остальных агентов, в том числе для
тех, которых нет на этом компьютере. Если обычного нет, а всем известным агентам
назван один и тот же скилл, это скилл действия: правило хранит его один раз, как скилл
для всех агентов, и его получат и агенты, добавленные позже. Агент, которого правило
называет сверх известных, сохраняет рядом свой скилл или его отсутствие
(`--skill AGENT=`). Пока приходит `agent_settings_problem`, ничего не объединяется.
Пустой `--skill` убирает скиллы правила и передаётся отдельно.

ID — от 1 до 100 латинских букв, цифр, `.`, `_`, `:` или `-`, начинается с буквы или
цифры; существующий ID отклоняется. `--project` должен называть проект,
зарегистрированный в этом workspace; вместе с `--project-path` они должны совпадать.
Текст — не больше 2000 символов, а все правила workspace вместе — не больше 20000,
потому что агенты загружают их полностью; изменение, которое их не удлиняет,
принимается, даже если они уже больше этого (правила более новой версии Richi тоже
считаются). `--text -` читает текст из stdin без
завершающего перевода строки; текст, который начинается с дефиса, передавай как
`--text="- ..."`. Концы строк хранятся как `\n`. `rules list` показывает все правила
workspace (`--global` или `--project ID` сужает список), общий размер всех правил в
`characters` (вместе с правилами более нового формата), зарегистрированные проекты в
`projects` и, если они есть, `invalid_rules`.

## Измени или удали правило

```sh
richi --compact-json rules list --project example
richi --compact-json rules update branch-naming \
  --expected-updated-at 2026-01-02T03:04:05.000000Z --text "Name branches EX-<number>_<topic>."
richi --compact-json rules remove branch-naming \
  --expected-updated-at 2026-01-02T03:04:05.000000Z
```

Передавай `updated_at`, прочитанный из `show` или `list`. Если правило за это время
изменилось, команда завершится ошибкой без записи: прочитай его снова и согласуй с
просьбой пользователя. `update` меняет текст, скиллы, источник (пустой `--skill`
или `--source` удаляет значение) или несколько полей сразу; параметры `--skill`
заменяют все скиллы правила. Чтобы сменить область правила, добавь новое и удали
старое.

## Посмотри, что менялось

```sh
richi --compact-json rules log
richi --compact-json rules log --id branch-naming --entries 5
```

Каждое изменение правила сохраняется в workspace, последние 200. Команда показывает
20 (`--entries` — до 200), новые сначала, а `more` говорит, хранятся ли более старые:
время `at`, `id` правила, действие `action` (`created`, `updated` или `removed`),
`by`, определённый агент `agent` и правило до и после изменения в `before` и
`after`. `by` — идентификатор чата оболочки, которая выполнила команду, или
`richi map` для изменения из карты; у самого правила те же значения его последнего
изменения лежат в `changed_by` и `changed_by_agent`. Это запись для проверки пользователем, а не
доказательство: тот, кто запускает команду, сам выбирает её окружение. Чтобы вернуть
правило по просьбе пользователя, добавь или измени его с текстом из `before`.

```sh
richi --compact-json rules clear-log --id branch-naming
richi --compact-json rules clear-log
```

Журнал хранит тексты правил, включая удалённые, и попадает в резервные копии. Очищай
его, для одного правила или целиком, только по просьбе пользователя, например когда в
правило попало то, что не должно оставаться в хранилище.
Запускай очистку без `--project-path`, в том числе при использовании `--id`.
Если правило удалили и создали заново, у одного ID может быть история в нескольких проектах.

## Примени изменение, заданное в JSON

```sh
richi --compact-json rules apply --json rule-change.json
```

```json
{"action": "add", "id": "review-skill", "scope": "global",
 "text": "Use the code review skill for every review.",
 "skill": "code-review", "skills": {"claude": "engineering:code-review"},
 "source": "cursor:EXAMPLE"}
```

`rules apply` принимает то же изменение, что `add`, `update` и `remove`, одним
объектом: `action`, `id` и поля этого действия. У `add` это `scope` (`global` или
`project` вместе с `project`), `text` и при необходимости `skill`, `skills` и
`source`; у `update` — `expected_updated_at` и то, что меняется; у `remove` —
`expected_updated_at`. `skill` — скилл для всех агентов, `skills` сопоставляет ID
агента его собственный скилл; обновление, которое называет любое из них, заменяет
оба. `--json -` читает объект из stdin, что удобно для текста с кавычками и
переносами строк. Действуют те же правила о явной просьбе пользователя.

## Правила в карте

Вкладка карты **«Правила»** показывает все правила workspace по областям, со
скиллами и объёмом, и отмечает скилл, которого нет у агента. Страница, открытая
командой `richi map`, добавляет, меняет и удаляет правила: шаблоны собирают правило со
скиллом («при … используй скилл …») или формат имён. Поле скилла принимает один скилл
для всех агентов; если у какого-то агента выбранного скилла нет, поле переходит к
отдельному списку для каждого агента и предлагает скилл с тем же именем после
префикса плагина. Списки берутся оттуда, где каждый известный агент хранит скиллы:
из его каталогов скиллов, встроенных скиллов и плагинов, а для Claude Code ещё и из
плагинов claude.ai, которые установило приложение Claude; скилл плагина называется `плагин:скилл`, как его
называют агенты, а скиллы, которые агент запускает только по вызову пользователя, не
показываются. Карта принимает изменения правил и настроек агентов
([AGENT_SKILLS.ru.md](AGENT_SKILLS.ru.md)) и только с такой страницы; знания остаются
только для чтения. Любая другая страница, например открытая по закладке, вместо
записи собирает команду `richi rules`, в которой назван workspace или хранилище,
показанное картой. Для workspace `default` или произвольной базы выполни
собранную команду с явным путём к базе в терминале. У правил, добавленных
в карте, источник — `richi map`, и журнал изменений указывает карту для каждого
сделанного в ней изменения. Карта предлагает удалить нечитаемое правило, если
его ключ однозначно указывает на одну строку.

## Предпочтения, сохранённые как записи

После обновления в выбранном workspace можно разобрать прежние записи
`preference:*`. Поле `preference_review` в ответе `rules show` содержит
краткую выборку для текущей области. Покажи её пользователю. Открой полный
список, чтобы согласовать точную формулировку и область каждого правила.

```sh
richi rules review-preferences
richi rules review-preferences --limit 3 --after preference:branch-naming
richi --project-path /work/example rules review-preferences
richi rules promote preference:branch-naming --project example --expected-updated-at 2026-01-02T03:04:05.000000Z
```

Подставь прочитанный `updated_at`. При подтверждении текст из `summary`
становится правилом со ссылкой на исходную запись. Пользователь может выбрать
другую формулировку через `--text`, иной ID через `--rule-id` или конкретную
проверку ветки через `--forbid-branch-prefix` или `--branch-format`. Записи без
привязки к проекту допускают `--global`. Если несколько проектов ожидают решения,
одна запись перечисляет их в `scopes` с отдельным ID правила для каждого проекта.
Пользователь подтверждает каждую область отдельно. Для следующей страницы передай
`next_after` в `--after` с теми же workspace и проектом. Если отмечено
`text_truncated` или `title_truncated`, прочитай полный оригинал через `read_more`
до подтверждения. Когда пользователь решает оставить запись
обычным знанием, передай `--dismiss`. После любого из этих решений подсказка
для этой области исчезает. Для переноса отклонённой записи заново прочитай её и
получи новое явное подтверждение перед вызовом с `--reconsider-dismissed`.
Если ранее созданное правило удалили или заменили, повторный перенос вернёт
конфликт. Исходная запись и её источники остаются доступны.
