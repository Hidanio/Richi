# Энциклопедия понятий

Энциклопедия — представление существующих `entities` с `kind: concept`.
Она использует ту же SQLite-базу, историю, источники и граф. Миграция схемы
и отдельный MCP не нужны. На сайте переключатель «Энциклопедия» открывает
каталог определений; карточка ведёт к источникам и связанным узлам карты.

## Одно название, несколько значений

Единица знания — **понятие в определённом контексте**, а не уникальное слово.
Одинаковые aliases допустимы у разных карточек. Поиск не объединяет их.
Например, `Y — координата в графическом редакторе` и `Y — целевая переменная модели`
могли бы быть разными понятиями, если оба значения подтверждены источниками.
Это пример различения смыслов, а не утверждение о наличии второго значения
в какой-либо реальной системе.

Различайте следующие ситуации:

| Ситуация | Как сохранять |
|---|---|
| Русское/английское название, сокращение, иное написание того же смысла | `aliases` одной карточки |
| Другой смысл, контракт, компонент или область применения | Отдельный `concept` с контекстом в ID и названии |
| Уточнение формулировки при том же смысле | Обновление карточки с `expected_updated_at`; история сохраняется |
| Изменение смысла/контракта со временем | Отдельный вариант с версией/периодом в контексте; связь `supersedes` только при доказанном замещении |
| Два несовместимых объяснения без достаточных доказательств | Явные альтернативы `hypothesis`; не выбирать одно как факт |

Параллельно используемые версии остаются `confirmed` в своих областях.
Старую карточку отмечайте `superseded`, только если подтверждено, что её
заменили в указанном контексте. Дата `verified_at` — дата проверки источника,
не дата появления определения или выпуска версии. Известные периоды действия
и версии указывайте в контексте; неизвестные даты не выдумывайте.

## Карточка

Рекомендуемый стабильный ID: `concept:<project-or-domain>:<term>:<scope>`.
В названии должны быть термин и различающий контекст. Например:
`Y — координата в графическом редакторе`.

Используйте короткие смысловые разделы в `summary`:

```text
Определение: 1–3 предложения о смысле понятия.

Контекст: проект, компонент/API, версия или период, если известны.

Пример: небольшой пример использования, подтверждённый источником.

Ограничения: существенные особенности и отличия от похожих понятий.
```

Первый абзац используется как краткое определение в каталоге. Не добавляйте
пустые разделы и искусственные примеры ради шаблона. Исследование и история
задачи остаются в своих записях; определение связывается с ними, а не копирует
весь разбор. В `sources` указывайте проверенные места кода/документации, при
возможности устойчивые ссылки на commit. Локально проверенный код не доказывает
состояние production. Для `confirmed` наличие источника проверяется CLI;
содержание источника проверяет агент.

Поля entity и команды записи описаны в [GRAPH.md](GRAPH.md). Обновление полностью
заменяет payload: сначала `entity get ID`, сохраняйте источники и остальные
поля, передавайте `expected_updated_at`. Новую карточку записывайте с
`expected_updated_at: null`, чтобы не затереть параллельную запись.

## Область применения и связи

Область проекта задаётся существующим явным ребром:

```text
entity:concept:... --used_in--> project:<project-id>
```

Для отображения области и повышения приоритета в `recall` учитываются только
прямые подтверждённые связи `used_in` с источником в этом направлении.
Связность графа, одинаковые теги и упоминание проекта не задают область понятия.
Если карточка справедлива для нескольких проектов, добавьте несколько таких
связей. Если контракт различается — создайте разные карточки. Отсутствие связи
означает «область проекта не задана», а не «универсальное определение».

Дополнительные связи создавайте только по свидетельствам:

- `variant_of`: частное определение → более общее понятие;
- `supersedes`: новое значение/контракт → заменённое старое;
- `references`: определение → разбор или задача с подробностями;
- `related_to`: смысловая связь, пояснённая в описании ребра.

Совпадение слова не доказывает `variant_of` или `related_to`. Связь
`supersedes` сама по себе не меняет `knowledge_state` старой карточки.
Между записями одного слова может вообще не быть смысловой связи.

## Чтение

```sh
richi recall 'Что такое Y?' --project service-example
richi recall 'BIT-vector' --max-chars 16000
richi entity get concept:example:term:scope
richi graph neighbors entity:concept:example:term:scope --depth 1
```

ID `concept:example:term:scope` демонстрационный. Фактический ID возвращает
`recall`. Короткие термины ищутся по явным aliases понятий, а не по совпадению
одной буквы внутри произвольного текста. Название/aliases должны отражать
используемое написание; полноценная морфология и embeddings не добавляются.

При нескольких подходящих понятиях `recall` сообщает `ambiguity` с вариантами.
`--project` повышает приоритет контекста и не превращает совпадение в единственно
возможное значение. Лимит и бюджет могут скрыть часть вариантов — смотрите
счётчики пропусков. Перед выводом прочтите полную релевантную карточку.
Если контекст задачи различает значения, используйте его и назовите выбранную
область; если нет — кратко покажите варианты и уточните смысл.

По умолчанию гипотезы и устаревшие определения скрыты. Для исторического
вопроса используйте нужные флаги и при необходимости историю карточки.
Энциклопедия показывает загруженный экспорт графа; при усечении экспортом
интерфейс предупреждает об этом. Отсутствие в каталоге не доказывает отсутствия
знания во всей базе.

## Как пополнять

Во время реальной работы выделяйте понятие, если его объяснение понадобится
повторно, смысл специфичен для системы или ошибка трактовки влияет на решение.
Сначала ищите существующие значения, затем проверяйте источники и контекст.
Выбирайте синонимы и теги самостоятельно по реальному употреблению. Не создавайте
массовый словарь общих терминов без связи с проектной работой. Не превращайте
неподтверждённую догадку в определение. Фонового импорта разговоров нет.
