# Диагностика отсутствующей известной записи

[English](RECALL_DEBUG.md) | Русский

Используй тот же привязанный workspace, проект/путь, запрос, флаги состояний, лимит результатов
и разумный бюджет вывода, что и в неудачном поиске. Другой успешный запрос —
контрольная проверка, а не доказательство работоспособности исходного. Если точный ID известен,
полный `entry get ID` или `entity get ID` устанавливает, существует ли запись;
предварительный поиск не требуется.

```sh
richi --compact-json --project-path /work/example recall 'why pooling was rejected' \
  --project service-example --expect entry:experiment:pooling --limit 8 --max-chars 16000
```

`--expect` принимает один полный ref `entry:<id>` или `entity:<id>` и включает
`--explain`. Без ожидаемого ID `--explain` даёт общий отчёт по этапам.
Читай реально зафиксированную причину: отсутствие записи, фильтр состояния, лексический guard,
отбор кандидатов, ранг/лимит результатов или бюджет вывода. Прямая лексическая
причина отказа отличается от итогового результата: confirmed-связь графа с источником может добавить
запись позже. Пустой ограниченный ответ не обязательно означает `no_match`.

Диагностика делит `--max-chars` с результатами. Проверяй пропуски, покрытие и
бюджет; отсутствие подробностей или счётчиков не означает ноль. При сравнении неизменного
поведения поиска сохраняй обычный recall отдельно, поскольку добавление
диагностики может уменьшить число показанных карточек. Эти флаги объясняют алгоритм;
они не меняют ранжирование, не проверяют знания и не вызывают LLM.

Для лексического пропуска попробуй наблюдавшиеся формулировки или RU/EN-термины как контроль.
Сохраняй исходный запрос, ожидаемый ref и наблюдавшуюся ошибку. Не придумывай aliases, не меняй
состояния, не сужай тестовый корпус и не переписывай знания ради успешного теста.
Отсутствие совпадений не доказывает, что работы не было. Перед использованием выводов прочитай полные
соответствующие текущие записи и сохрани условия эксперимента.

Про `entries_scanned`, `entries_scored`, предварительный routing-фильтр и внутреннюю работу FTS
читай только [DIAGNOSTICS.ru.md](DIAGNOSTICS.ru.md#счётчики-предварительного-отбора-entries).
Само по себе уменьшение числа оценённых payload не доказывает поиск за постоянное время или лучшее качество recall.
Для оценки регрессий и качества используй [EVALUATION.ru.md](EVALUATION.ru.md).

Известное ограничение FTS: нормализация запроса заменяет кириллическую `ё` на `е`, но
текущий индекс хранит исходное написание. Заголовок с `берёза` может
не находиться в recall ни по `береза`, ни по `берёза`. Чтение по точному ID остаётся
доступным. Сохраняй это как ошибку поиска; не переписывай запись,
не придумывай aliases и не перестраивай рабочий индекс только ради сокрытия расхождения.
