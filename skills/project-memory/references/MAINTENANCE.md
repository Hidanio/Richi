# Ручное обслуживание памяти

Этот режим запускается только по прямому запросу пользователя: «уборка памяти»,
«объедини дубли», «обслуживание базы знаний» или «memory GC».
Это работа агента в явно запрошенной задаче, а не расписание или фоновый процесс.
Во время обычных проектных задач не запускать полную ревизию базы.

Цель — повысить полезность активной памяти: объединить настоящие дубли,
сохранить различия, убрать повторение, восстановить подтверждённые связи.
Число удалённых карточек и уменьшение размера SQLite не являются метрикой успеха.

## Запуск и область

Достаточно отдельной задачи с запросом:

> Используй project-memory. Проведи ручное обслуживание общей памяти:
> найди дубли и разрозненные знания, объедини обоснованные совпадения,
> сохрани источники, ограничения, историю и варианты определений.
> Перед изменениями сделай backup. Покажи изменения, проверки и спорные случаи.

Если указан проект или тема, ограничь работу ими. `graph export --project`
возвращает связную компоненту, а не строгую область проекта: соседство само
по себе не разрешает менять чужие знания. При запросе общего обслуживания
рассмотри каталог целиком, но полные карточки читай только для кандидатов.
Если пользователь просит только аудит/предложения, не меняй знания.
Запрос на уборку разрешает обоснованные обратимые правки в этой области;
отдельного согласования каждого объединения не требуется.

## Недорогой отбор кандидатов

CLI: `richi`. Ниже приведены подкоманды; укажите перед ними `richi`. Настроенную базу показывает `richi config show`.

1. Выполни `punisher --limit 20 --max-chars 16000`, при известном проекте добавь
   `--project ID`. Отчёт уже включает проверку SQLite и коротких кандидатов:
   недостающие источники, даты, связи, точные повторы и общие aliases.
   Гипотезы и старые даты — повод для просмотра, а не дефекты по определению.
2. Сохрани JSON в рабочий файл. Если для выбранной группы нужен каталог связей,
   используй `graph export --include-hypotheses --include-superseded`.
   Не выводи всю базу в контекст; дочитывай содержание отобранных карточек.
3. Это признаки для просмотра, а не доказательства дубля. Начни с точных
   повторений и явных пересечений; не назначай сходство текста основанием
   для автоматического слияния.
4. Проверь `coverage`, `truncated` и лимиты отчёта/экспорта. Если область неполна, используй
   разбиение области или согласованный read-only снимок для локального
   перечисления метаданных. Не объявляй всю базу проверенной по усечённому
   каталогу. Изменения всё равно выполняй только через CLI.
5. Обрабатывай кандидатов небольшими группами, например до 10 групп за шаг.
   Полностью дочитывай их через `entry/entity/edge get`; историю — когда
   нужны прежние значения, причины или хронология. Продолжай до завершения
   выбранной области либо явного пользовательского лимита; отмечай остаток.

Не перечитывай подряд все репозитории, Jira и всю историю. Внешний источник
перепроверяй, когда это нужно для конкретного вывода. Недоступный файл помечай
как пробел источника и ищи уже известную устойчивую замену; это само по себе
не делает историческое знание ложным. Возраст, редкое использование и отсутствие
связей тоже не доказывают бесполезность карточки.

## Решение для каждого кандидата

| Ситуация | Действие |
|---|---|
| Один смысл, область и версия; содержание дублируется | Объединить в канонической карточке с сохранением всей полезной информации |
| Дополняющие друг друга короткие фрагменты одного знания | Собрать связное описание, сохранив происхождение утверждений |
| Исследование и извлечённое из него определение | Сохранить оба, связать; у них разные роли |
| Разные смыслы, версии, контракты, условия эксперимента | Оставить раздельно, добавить подтверждённые связи при необходимости |
| Противоречащие результаты | Сохранить обе позиции с условиями и источниками; не усреднять |
| Подтверждённо заменённый дубль или факт | `superseded` после сохранения замены и проверки её доступности |
| Стилистическое многословие | Сократить повторение, сохранив утверждения, числа, условия и ограничения |
| Неясная ценность или непроверенная причина | Оставить и включить в короткий список спорного |

Сохраняй неудачные эксперименты, причины отказов, исторические замеры,
условия воспроизведения и различие implemented/merged/released. Они не мусор.
Не повышай гипотезу до confirmed и не обновляй `verified_at` только потому,
что текст отредактирован. При объединении подтверждённого и неподтверждённого
содержания не помещай гипотезу под общую подтверждённую метку: оставь её
отдельной карточкой с собственным состоянием.

Предпочитай существующий устойчивый ID. Каноническая Jira-карточка `task:ABC-123`
остаётся доступной по номеру задачи; её краткость не основание поглотить её
разбором или понятием. Не объединяй разные сущности лишь из-за общего Jira,
источника, тега или синонима. Полный формат вариантов — в [ENCYCLOPEDIA.md](ENCYCLOPEDIA.md).

## Обоснованное объединение

Перед первой правкой сделай `backup` через CLI, сохрани возвращённый путь.
Для проверенной группы можно сохранить `sources snapshot --ref REF --output NEW.json`
(повтори `--ref` для остальных карточек). Перед применением плана выполни
`sources check --manifest NEW.json`: это обнаружит правки карточек, изменения
состава связей и дрейф локальных файлов. Manifest фиксирует прочитанные версии,
но не заменяет CAS и не блокирует последующие параллельные записи.
Составь локальный план `старые refs → канонический ref`: что совпадает,
что переносится, почему это одна область/версия, что требуется связям.
План нужен для проверки результата и восстановления, а не как обязательная
остановка на согласование. Спорные группы не объединяй.

1. Прочитай полные текущие payloads и `updated_at`. Подготовь каноническую
   запись, сохранив источники с labels/dates, смысловые синонимы, проектные
   привязки, измерения, оговорки и полезные прежние попытки в доступном тексте.
   История сама по себе недостаточна: обычный поиск её не читает.
2. Сохрани каноническую карточку с `expected_updated_at`, проверь через `get`.
   Для нового ID используй `expected_updated_at: null`. Конфликт означает
   новое параллельное знание: перечитай и пересобери группу, не затирай его.
3. Прочитай все входящие/исходящие связи кандидатов с нужными state-флагами.
   `neighbors` ограничен: проверь усечение; при необходимости используй
   сохранённый полный каталог/снимок для списка связей. Производные membership
   меняются через `entry.project_ids`, их не нужно дублировать.
4. Обоснованные отношения канонического узла сохрани/уточни с источниками
   и тем же смыслом направления и состояния. Не переноси автоматически
   причинность и область `used_in` между разными контекстами. Новые связи
   не должны образовывать бессмысленные self-loops. Рёбра с разными
   основаниями/состояниями не являются дублями только из-за одинаковых концов.
5. Запиши подтверждённую связь `supersedes` от канонического узла к дублю;
   источником основания может быть сохранённый отчёт сравнения с исходными
   refs/версиями и их источниками. Она описывает замену, но не делает redirect.
6. Только после проверки сохранения содержания и нужных связей отметь дубль
   `superseded`, сохранив его текст и источники. Добавь в его summary явную
   ссылку на канонический ref; исходную историю не переписывай. Уместные старые
   названия добавь канонической карточке как aliases, не смешивая смыслы.

Важно: сейчас автоматических redirects нет. `get OLD_ID` прочтёт старую карточку,
а обычный `recall OLD_ID` может не показать её после superseded. Связь с
устаревшим endpoint тоже скрыта обычным графом. Проверь исходные запросы и
входящие ссылки; сохраняй значимые стабильные ID активными, если перенос
ломает работу. Не скрывай такой разрыв обещанием «история сохранена».

Пакет `entry put`, `entity put` или `edge put` атомарен внутри своей команды;
несколько команд не являются одной транзакцией. При сбое оставь старое знание
активным, если замена ещё не готова, и сообщи выполненные шаги. Параллельные
записи других задач не откатывай восстановлением старого backup поверх всей БД.
Для точечного возврата читай историю и применяй полные payloads через CLI с CAS.

## Проверка и отчёт

- `check` и полное чтение изменённых карточек/связей.
- Повтор исходных запросов по теме/синониму/Jira: нужное знание доступно,
  источники и ограничения сохранены, разные значения остаются различимыми.
- Исторические карточки доступны через `get` и соответствующие state-флаги.
- Если менялся код поиска, используй [EVALUATION.md](EVALUATION.md).
  Для обычной уборки достаточно проверок затронутых случаев; не меняй ожидания
  старых тестов, чтобы скрыть потерю знания.
- Отчёт: область и покрытие, backup, группы до/после, правки связей, проверенные
  запросы, оставленные спорные случаи и остаток работы. Количество карточек
  само по себе не доказывает улучшение. Если подходящих изменений нет, так и скажи.

При содержательных изменениях сохрани одну сводку обслуживания со ссылкой на
отчёт и затронутые refs. Не создавай запись на каждую проверенную карточку
и отдельный «успешный запуск», если ничего полезного не изменилось.

Этот режим сохраняет данные логически: подтверждённые дубли уходят из обычной
выдачи, но остаются читаемыми с историей. CLI не предоставляет физического
удаления. Не обходи его прямым SQL, не удаляй историю, исходники, вложения,
backup или WAL/SHM. Не запускай VACUUM, миграции или перестройку индексов ради
ритуальной «оптимизации» без отдельной технической причины.
