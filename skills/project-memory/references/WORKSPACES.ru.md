# Workspaces, членство репозитория и runtime

[English](WORKSPACES.md) | Русский

Читай при выборе или смене workspace, разрешении ошибок членства или runtime, регистрации репозиториев и работе со связанными worktrees. Входной skill сохраняет правила доступа, нужные для каждой задачи.

<a id="runtime-and-storage"></a>

## Runtime и хранилище

Используй установленную команду `richi`. Выполни `richi config show`, чтобы определить выбранный runtime, базу и каталог данных; никогда не предполагай имя пользователя, путь репозитория или каталог конкретного агента. Если executable не находится в PATH, используй путь установки, настроенный для этого агента, или сообщи об отсутствии установки. SQLite — основное хранилище; Markdown — только документация. Держи базы, Git-снимки, runtime-файлы и backups вне исходного checkout.

Все фрагменты команд ниже — подкоманды `richi`, например `richi recall "query"`. Глобальные селекторы идут первыми, например `richi -w NAME recall "query"`. Прямые переопределения `--db`/`--config` предназначены для обычного терминала; обнаруженный чат использует зарегистрированную привязку. Соблюдай выбор хранилища в течение всей задачи; не переключайся молча на другую базу при ошибке. Команды не требуют MCP-сервера.

По умолчанию runtime — фиксированный установленный пакет. Разработка выбирается для текущего workspace через `richi config set development.source /path/to/Richi` и `richi config set dev true`; `richi config set dev false` возвращает установленный код. CLI, агенты и карта используют этот общий выбор и настроенную базу. Не меняй режим только ради чтения знаний. Просмотр конфигурации и отключение dev работают через установленный launcher, даже если исходники разработки сломаны или отсутствуют. Выбор runtime никогда не мигрирует SQLite; для экспериментов со схемой используй отдельное хранилище.

Изменения launcher требуют переустановки фиксированного пакета даже при `dev=true`; одной перезагрузки исходников недостаточно.

## Выбор чата и членство репозитория

- В начале каждого нового чата выполни `richi chat current` и `richi workspace list` до поиска или записи знаний. Если чат не привязан и пользователь явно не назвал workspace в этом чате, спроси один раз: использовать текущий workspace CLI или выбрать другой для этого чата. Даже один доступный workspace не означает неявного согласия. Пока ждёшь ответ, продолжай независимую работу с репозиторием; не читай и не записывай память до выбора.
- После выбора пользователя выполни `richi chat bind --current`, чтобы зафиксировать текущий workspace CLI, или `richi chat bind NAME`, чтобы переопределить его только для этого чата. Привязка сохраняется между ходами; не спрашивай снова в том же чате или после сжатия контекста. Существующий чат с уже явно выбранным workspace может привязать этот известный выбор без повторного вопроса. Никогда не выводи выбор только из cwd, членства проекта или глобального значения CLI по умолчанию.
- Launcher обнаруживает `CODEX_THREAD_ID` Codex; другие интеграции должны передавать стабильный уникальный `RICHI_CHAT_ID` или `--chat ID` при каждом вызове. Не выдумывай новый ID для обхода привязки и не убирай идентификатор чата для доступа к другому хранилищу. Обнаруженный непривязанный чат не может читать или записывать знания. Новые чаты и ответвления выбирают независимо; делегированная работа наследует подтверждённый workspace родителя с переданным идентификатором чата, а не выбирает новое глобальное значение по умолчанию.
- Привязка чата имеет приоритет над CLI default. `-w NAME` может для ясности повторять привязанный workspace, но не менять его. Используй `chat bind NAME --replace`, только когда человек явно меняет workspace этого чата. Не используй глобальный `richi use` для задач чата. Прямые переопределения базы/config/data-directory отклоняются даже при совпадении путей; устраняй их без обхода привязки. Обычные терминальные команды вне контекста чата сохраняют поддержку явной пользовательской конфигурации.
- После выбора `richi --project-path /path/to/checkout status --project PROJECT_ID` даёт компактный отчёт о workspace/runtime/storage и членстве; без пути проверяется cwd. `status` до привязки возвращает только метаданные выбора, не разрешение читать знания. Считай `selection_required` и `unavailable` нерешёнными; при `attention` изучи issues и coverage. Exit 0 означает, что отчёт создан, а не что workspace исправен. Используй `status --projects --limit 50` при проверке зарегистрированных путей, а не рутинно для каждой задачи. Он читает только метаданные реестра, никогда не исправляет пути и не мигрирует хранилища; неполные проверки не подтверждают членство. Подробности: [DIAGNOSTICS.ru.md](DIAGNOSTICS.ru.md).
- Для работы с репозиторием проверь `richi project check /path/to/checkout --id PROJECT_ID` в привязанном workspace. Изучи возвращённые status, workspace, database и project до использования совпадения. Могут совпадать точные пути, подкаталоги и связанные Git worktrees; повторяющиеся идентичности проектов, вложенные незарегистрированные репозитории и отсутствующие пути требуют разрешения. Один проект может входить в несколько workspaces; это никогда не переопределяет выбор чата.
- Закрепляй операции репозитория параметром `--project-path /path/to/checkout` перед подкомандой, например `richi --project-path /path/to/checkout entry put --json FILE`. Членство перепроверяется в транзакции операции; явный `--project` должен совпадать, а `project_ids` entry — включать проверенный проект. Межпроектные записи могут дополнительно указывать проекты выбранного workspace. Для общих понятий workspace или администрирования путь можно намеренно не указывать. Проверка не устанавливает смысловую корректность заметки и не проверяет каждый внешний источник.
- `project scan ROOT` предварительно показывает ограниченное обнаружение Git-репозиториев в родительской папке; `project scan ROOT --apply` регистрирует полный результат без конфликтов. Сначала прочитай предварительный результат. Worktrees одного репозитория группируются, существующие метаданные сохраняются, неполное обнаружение или конфликты останавливают применение. Код и знания не копируются, постоянное наблюдение за папкой не создаётся. `project add PATH` по-прежнему регистрирует одну папку; `workspace create NAME` создаёт настройки, а `-w NAME init` — пустое хранилище из обычного терминала.
- Каждый workspace владеет своими знаниями, историей, графом, понятиями и Git-артефактами. `default` сохраняет прежнюю память. Не ищи, не копируй и не мигрируй знания другого workspace без разрешения в рамках задачи. Общие исходные пути остаются общим кодом; независимые правки требуют отдельных checkouts/worktrees. Работающие карты закреплены за исходным workspace. Настройки dev после наследования при создании workspace независимы.
