# Инструменты и их применение

[English](TOOLS.md) | Русский

Используй эту процедуру для линтеров, тестовых клиентов, профилировщиков и других
инструментов, опыт применения которых нужен в следующих задачах и проектах.
Соблюдай привязку workspace и проверку репозитория из [SKILL.ru.md](../SKILL.ru.md).
Карточки используют `entity.kind: tool` и требуют схему 3; явная миграция описана
в [GRAPH.ru.md](GRAPH.ru.md). Чтение и выбор runtime никогда не мигрируют базу.

## Выбери запись

| Знание | Запись |
|---|---|
| Что делает инструмент, основные команды, общие ограничения | Сущность `tool` |
| Определение понятия, например линтинга или семплирования | Сущность `concept`, если определение нужно самостоятельно |
| Повторяемый рецепт, настройки проекта или сценарий с несколькими инструментами | Запись `procedure` |
| Конкретная попытка, её параметры, наблюдения и результат | Запись `experiment` или `investigation` |
| Текущая цель и решение по основной работе | Запись `task` |

Инструменту не нужен обязательный дубль в понятиях. Одна процедура может
использовать несколько инструментов и относиться к нескольким проектам через
реальные `project_ids`. Одинаковый рецепт храни один раз; несовместимые настройки
разделяй с явным контекстом. Отдельных типов профиля или запуска нет.

## Карточка инструмента и практические детали

Предпочитай устойчивый ID вроде `tool:tracekit`. Начни `summary` с назначения,
затем добавь полезные команды, входы/выходы, ссылки на настройки и ограничения.
Это обычные разделы текста, а не разбираемые программой поля. В `aliases`
добавляй встречавшиеся названия; не выдумывай синонимы для расширения поиска.

Команды конкретного проекта, пути настроек, версии, окружение и роли храни
в процедуре. Ссылайся на авторитетный конфигурационный файл, а не копируй его
целиком в память. Для рецепта с двумя проектами укажи, какой является целью,
а какой предоставляет тестовое окружение. Дата конкретного запуска, кандидат,
параметры, результат и ссылки на артефакты принадлежат эксперименту/исследованию.
`work_state: done` означает завершение работы; это не означает успешную
квалификацию или принятие кандидата. Фактический исход опиши в `summary`.

Особенности CLI храни вместе с версией и проверенными условиями; наблюдаемое
исключение не становится безусловным свойством инструмента. Сохраняй доступность
параллельных рецептов и исторических результатов в поиске. Новая запись для
другого кандидата не заменяет автоматически прежний baseline. `verified_at` —
дата проверки свидетельств, отдельно от даты запуска или релиза.

## Канонические связи применения

```text
entry:procedure:example-check --uses_tool--> entity:tool:tracekit
entry:procedure:example-check --uses_tool--> entity:tool:benchkit
entry:experiment:example-attempt --uses_tool--> entity:tool:benchkit
entry:experiment:example-attempt --part_of--> entry:task:EXAMPLE-42
entity:tool:benchkit --used_in--> project:service-example
```

ID демонстрационные. Каждой связи нужны осмысленное описание и проверенный
источник. Применение задаёт **подтверждённое ребро `uses_tool` с источником от
entry к инструменту**. Прямая связь задачи допустима, если свидетельство
содержится в самой задаче. Подробная запись может вести к своей задаче через
подтверждённую связь `part_of` с источником в показанном направлении. Указывай
реальную принадлежность entries проектам; общий тег, одинаковый Jira key или
произвольная близость в графе не доказывают применение. Для показа задачи через
подробную запись в проекте и запись применения, и задача должны принадлежать
этому проекту; принадлежность родителя не расширяет область дочерней записи.

Необязательная связь `tool --used_in--> project` утверждает применение в
указанном контексте, например тестирование проекта. Она не устанавливает
runtime-зависимость, не привязывает к инструменту все задачи проекта и не
доказывает применение в конкретной задаче. Роль и условия опиши в ребре.
`depends_on` используй только при подтверждённой зависимости.

Раздел «Инструменты» ведёт по пути инструмент → проект → связанные задачи.
Задачи попадают туда только через собственное явное свидетельство применения
или связанные подробные записи и в рамках выбранного проекта. Самостоятельные
сценарии показаны отдельно. У проекта только со связью `used_in` может не быть
связанных задач; это недостаток сведений о задачах, а не основание перечислить
все задачи проекта. Неизвестная область применения остаётся неизвестной.

## Чтение и запись

```sh
richi --compact-json tools list --limit 100
richi --compact-json tools get tool:tracekit
richi --compact-json --project-path /work/example entity get tool:tracekit
```

`tools list` возвращает короткие карточки инструментов и метаданные проектов/
применений. Лимит инструментов — 1–200, по умолчанию 100. Summary ограничен
1000 символами с признаком `summary_is_excerpt`; источники опущены с явным
счётчиком `sources_omitted`. Тексты применений, цепочки до задач и история для
каталога не загружаются. Карточки проектов содержат ID, имена и метаданные
навигации; полные описания, пути к репозиториям и источники загружает только
`tools get`. `detail` равен false, а количество задач — `null`,
то есть «не загружено», а не ноль. Следуй `read_more` или вызывай `tools get ID`
с собственным ID сущности инструмента.

`tools get` возвращает полную текущую карточку инструмента и общий словарь
`records`, ключи которого — полные entry refs. Массивы `records` инструмента/
проекта содержат ссылки в этот словарь. Связи задач внутри проекта содержат
`ref`, `usage_refs` и `usage_paths`, поэтому общие payload задач и применений
возвращаются один раз. Количество задач вычисляется в подробном представлении.
Записи применения включают свидетельства `uses_tool` с источниками;
`usage_paths` сохраняют refs связей `part_of` для отдельного `edge get`.
Обе команды не загружают историю ревизий; для хронологии используй
`entity get ID --history` или `entry get ID --history`.

Обе команды принимают `--include-hypotheses` и `--include-superseded`; при
переходе к подробностям сохраняй выбор состояний. Эти флаги не превращают
неподтверждённую связь или связь без источника в свидетельство применения.
Каждый вызов читает один снимок; между вызовами списка и подробностей возможны
изменения. Лимиты: 200 записей применения, 200 разных задач и 100 разных проектов
на инструмент, 200 разных посещённых предков на запись применения при обходе
`part_of`; сама запись применения не расходует лимит предков. Параллельные
связи не расходуют дополнительные места для проектов или предков. В подробной
записи показано не более 20 связей `uses_tool`; в карточке проекта — не более
20 refs прямых связей `used_in`, этот лимит указан в `limits.evidence_edges_per_project`.
Оба ограничения свидетельств отмечаются через `usage_evidence_truncated`,
который передаётся в общий признак усечения. Проверяй `truncated` и `limits`, прежде
чем считать количество полным: при усечении счётчики проектов, задач и применений
описывают возвращённую выборку. `total_tools` считает все инструменты,
соответствующие фильтрам состояния и ID.

Вкладка «Инструменты» читает каталог максимум из 200 инструментов независимо
от экспорта графа карты и загружает подробности при выборе инструмента.
`/api/tools?tool=ID` отдаёт подробности через тот же ограниченный выбранным
хранилищем worker только для чтения. Интерфейс предупреждает о неполноте при
усечении результата. Схема 2 остаётся доступной для чтения с пустым каталогом
инструментов до явной миграции и наполнения.

Перед созданием ищи существующие карточки. Используй названия и aliases из
источников; общий recall ищет инструменты вместе с другими сущностями. Для
известной карточки `entity get tool:tracekit` возвращает полный payload;
`entry get ID` и `edge get ID` — рецепты, запуски и свидетельства применения.
До повторного использования команды или сравнения результатов прочитай условия
и источники. Каталог и граф служат навигацией; короткое описание не заменяет
полной записи со свидетельствами.

Новую карточку и её связи записывай с `expected_updated_at: null`. Для обновления
сначала прочитай полный текущий payload, сохрани остальные поля и метаданные
источников, убери `created_at`, `updated_at`, `history` и передай прочитанный
`updated_at` как `expected_updated_at`. При конфликте перечитай и согласуй
изменения. Каждую запись проверь полным get. Поля сущностей/связей и пакетные
операции описаны в [GRAPH.ru.md](GRAPH.ru.md), entries — в
[ENTRY_WRITE.ru.md](ENTRY_WRITE.ru.md).

Для разделения существующего понятия или длинной задачи используй
[MAINTENANCE.ru.md](MAINTENANCE.ru.md). Сохраняй устойчивые ID и историю, если
объект остаётся тем же, контекст знаний и все подтверждающие источники.
Сначала создай и проверь нужные процедуры/запуски и связи, затем сокращай
исходную запись. Не переклассифицируй автоматически все понятия с упоминанием
инструмента и не копируй знания другого workspace без явного запроса.

## Демонстрационный пример

`TraceKit` описывает вымышленный клиент трассировки, `BenchKit` — вымышленный
нагрузочный клиент. Процедура «Сравнение кандидатов кеша» использует оба
инструмента и относится к `service-example` и `test-sandbox`. Её summary
задаёт их роли, конфигурационные файлы и повторяемые команды. Эксперимент
сохраняет одну датированную попытку, наблюдаемый результат и артефакты;
связан с `task:EXAMPLE-42` через `part_of`, а с реально использованными
инструментами — через `uses_tool`.

В BenchKit для `service-example` задача EXAMPLE-42 может появиться через этот
эксперимент. Другая задача того же проекта остаётся вне списка без собственного
свидетельства применения. «Попытка завершена» и «Кандидат прошёл проверку»
остаются разными утверждениями. Названия и обстоятельства иллюстрируют модель;
это не предзагруженные знания и не свидетельства о реальных инструментах.
