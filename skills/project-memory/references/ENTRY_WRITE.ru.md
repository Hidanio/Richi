# Создать или обновить запись

[English](ENTRY_WRITE.md) | Русский

Используй эту процедуру для `entry put`, в том числе для черновика, который не будет отправлен.
Выбор workspace, членство репозитория и разрешение на запись определяются
[SKILL.ru.md](../SKILL.ru.md). Запрос только на черновик не разрешает запись.

<a id="preserve-the-complete-payload"></a>

## Сохрани полный payload

`entry put` заменяет все сохраняемые поля; пропущенные необязательные поля сбрасываются к значениям по умолчанию.
Для существующего ID выполни `entry get ID`, скопируй полный payload, удали только
`created_at`, `updated_at`, `history`, затем внеси нужные изменения. Установи
`expected_updated_at` равным точному значению только что прочитанного `updated_at`. Сохрани не связанные
с изменением поля, источники и их метаданные, членство проектов, состояния и даты.
Не составляй обновление из recall, read, brief или выдержки графа.
Для нового ID используй `expected_updated_at: null` — только создание.

```sh
richi --compact-json --project-path /work/example entry get task:EXAMPLE-42
# Prepare a UTF-8 JSON file from that full result.
richi --compact-json --project-path /work/example entry put --json /tmp/entry-update.json
richi --compact-json --project-path /work/example entry get task:EXAMPLE-42
```

Конфликт означает, что запись изменилась: перечитай, согласуй изменения и повтори с новой
версией. Никогда не перезаписывай параллельную работу старым payload. Проверяй успешные
записи полным get; сообщай о неудачных или недоступных сохранениях. Используй транзакции CLI, не SQL.
Также поддерживается heredoc с кавычками и `--json -`. Один объект или массив до
1000 объектов атомарен в пределах одной команды; повторяющиеся ID отклоняются, вход
ограничен 10 миллионами символов. Отдельные команды не образуют одну транзакцию.

<a id="entry-fields"></a>

## Поля entry

Обязательны `id`, `kind`, `title`, `summary`. Выбираемые вызывающей стороной стабильные ID — не более
200 символов без управляющих символов, например `task:EXAMPLE-42`.

| Поле | Контракт |
|---|---|
| `kind` | `task`, `decision`, `fact`, `note`, `investigation`, `experiment`, `procedure` |
| `project_ids` | ID существующих проектов; по умолчанию `[]` для действительно общих знаний |
| `jira_key` | Необязательный реальный ключ Jira; никогда не придумывай его |
| `knowledge_state` | `confirmed`, `hypothesis` (по умолчанию), `superseded` |
| `work_state` | `planned`, `in_progress`, `implemented`, `merged`, `released`, `blocked`, `done` или `null` |
| `sources` | Объекты с обязательным `reference`; необязательными `label`, `type`, `observed_at`, `revision`, `locator`, `sha256`, `git`; по умолчанию `[]` |
| `tags`, `aliases` | Непустые строки, нормализуемые сортировкой и удалением повторов; по умолчанию `[]`; используй наблюдавшиеся термины |
| `verified_at` | Дата ISO, timestamp ISO с часовым поясом или `null`; дата проверки свидетельства, не обновляется автоматически |
| `expected_updated_at` | Точная версия из get для обновления; явный `null` для создания; не сохраняется |
| `event_id` | Необязательный уникальный ID доставки, только для entry; не сохраняется в payload |

Массивы проектов, источников, tags и aliases допускают по 100 элементов. Неизвестные поля и типы
отклоняются. Подтверждённые факты и решения требуют хотя бы один источник; его наличие
не доказывает истинность. Создавай структурированный `source.git` через
[GIT_CAPTURE.ru.md](GIT_CAPTURE.ru.md); точные ручные привязки: [DIAGNOSTICS.ru.md](DIAGNOSTICS.ru.md#точные-источники-в-записях).

Одинаковое нормализованное содержимое возвращает `unchanged` без новой ревизии истории,
даже с устаревшим CAS. Повторное использование `event_id` с тем же нормализованным payload возвращает
`replayed`, даже после последующих правок; другое содержимое с тем же ID — ошибка.
Для нового изменения используй новый event ID или не указывай его. Другие статусы —
`created`/`updated` в `results`. Записи entity/edge не принимают `event_id`;
их отдельные payload описаны в [GRAPH.ru.md](GRAPH.ru.md).

<a id="write-useful-current-knowledge"></a>

## Записывай полезные текущие знания

Сохраняй стабильный ID задачи и связную summary текущего решения, причин,
области применения, существенных условий и исключений, свидетельств, состояния реализации,
неизвестного и следующего шага. Длина summary 1000–3000 символов — необязательный ориентир, не лимит
и не разбираемый шаблон. Заменяй устаревший текущий статус вместо бесконечного
дописывания хронологии. Заголовки Markdown и runtime Templates не требуются.

Неудачный эксперимент может быть confirmed в наблюдавшихся условиях;
непроверенное объяснение остаётся hypothesis. Отказ не означает supersession.
Различай implemented, merged и released; не продвигай `verified_at`
только потому, что изменился текст. Отдельно сохраняй даты измерений и событий.
Используй реально проверенные источники и привязки revision/hash, а не отсутствующие файлы или догадки.

Полезные самостоятельные подробности выноси в entries `investigation`, `experiment` или `decision`
с собственными источниками, состояниями, реальными проектами и Jira key. Сохраняй их
refs и действующие ограничения в summary задачи. Текущий текст доступен поиску;
история — нет. История сохраняет полные ревизии до/после и создание,
но не заменяет доступные текущие свидетельства. Читай её, только когда нужна хронология.
Для разделения существующей задачи, объединения записей или изменения связей при очистке
используй [MAINTENANCE.ru.md](MAINTENANCE.ru.md); дочерние записи и связи нужно проверить до
сокращения родительской. Обычная правка одной записи не требует процедуры обслуживания.
