# Стабильные релизы GitHub

[English](RELEASING.md) | Русский

Обновлятор Richi читает стабильные релизы из
[Hidanio/Richi](https://github.com/Hidanio/Richi/releases). Он принимает только
строгие версии `X.Y.Z` и теги `vX.Y.Z`. Draft и prerelease исключены.
Публикации в PyPI и отдельного сервера обновлений нет.

Для подготовки релиза обновите `[project].version` в `pyproject.toml` и
`__version__` в `src/richi/__init__.py`, проведите ревью и объедините изменение,
затем отправьте соответствующий тег `vX.Y.Z`. Отправка тега запускает
`.github/workflows/release.yml`. Workflow собирает один wheel и проверяет именно
этот артефакт на Python 3.9 и 3.12 в Linux и macOS, включая публичную оценку recall.
Только после успеха всех заданий матрицы создаётся GitHub draft с прикреплёнными
wheel, manifest и установщиком, а затем он публикуется. Неудачная загрузка
оставляет draft, невидимый обновлятору; проверьте или удалите его перед повторной
публикацией. Опубликованные версии нельзя заменять: исправления получают новую
версию и тег.

Не публикуйте пустой релиз кнопкой **New release** в GitHub, пока выполняется
workflow: обновлятор увидит его до появления manifest и wheel, а финальный шаг
`gh release create` рассчитывает сам создать релиз. Отправляйте только тег;
публикацию проверенных артефактов выполняет workflow.
Тег `v1.0.0` был опубликован из кода с версией `0.1.0`, поэтому проверка упала.
Исправленная версия — `1.0.1`, с новым тегом на коммите исправления версии.
Старые теги сохраняются. После слияния исправления и обновления `main` проверьте
сборку и отправьте только нужный тег:

```sh
git switch main
git pull --ff-only origin main
python -m build --wheel --outdir dist_release
python scripts/release_manifest.py dist_release/richi-1.0.1-py3-none-any.whl --tag v1.0.1 --output dist_release/richi-release.json
git tag v1.0.1
git push origin refs/tags/v1.0.1
```

Выполняйте команды тега только после успешных сборки и проверки. Дождитесь
успеха всех заданий релиза, включая публикацию, затем запустите
`richi update check`. На совместимой старой установке ожидаются версия `1.0.1`
и `can_apply: true`. Если задание релиза упало, изучите его лог, прежде чем
передавать ссылку установщика коллегам.

По умолчанию workflow использует `contents: read`. Только финальное задание
публикации получает `contents: write` через встроенный `GH_TOKEN`; оно не
выполняет код checkout. Последовательность создания draft и публикации следует
[командам релизов GitHub CLI](https://cli.github.com/manual/gh_release_create).

Для локальной подготовки без публикации:

```sh
python -m build --wheel
python scripts/release_manifest.py dist/richi-1.0.1-py3-none-any.whl --tag v1.0.1
python scripts/build_installer.py dist/richi-1.0.1-py3-none-any.whl
python tests/installer_release_smoke.py dist
```

`scripts/release_manifest.py` проверяет имя wheel, метаданные пакета, встроенную
версию исходников, версию исходного checkout и необязательный тег, прежде чем
записать детерминированный `dist/richi-release.json`. Manifest содержит только
публичные метаданные совместимости, имя wheel, его SHA256 и размер в байтах:

```json
{
  "format_version": 1,
  "version": "1.0.1",
  "updater_protocol": 1,
  "python_min": [3, 9],
  "database_schemas": [1, 2],
  "map_schema": 2,
  "wheel": {
    "filename": "richi-1.0.1-py3-none-any.whl",
    "sha256": "<64 lowercase hexadecimal digits>",
    "size": 123456
  }
}
```

Поля совместимости описывают этот runtime и требуют пересмотра при изменении
требований к Python, схеме SQLite или карте. Новые форматы manifest или протоколы
обновлятора требуют явного пути обновления launcher. Клиент ограничивает wheel
размером 50 МиБ и проверяет контрольную сумму и метаданные до установки.
Загрузка начинается с фиксированных URL репозитория и следует перенаправлениям
только на хосты артефактов релизов GitHub. Ни одно поле manifest не может выбрать
хост загрузки или команду. SHA256 обнаруживает повреждение; подлинность издателя
опирается на GitHub HTTPS и контроль официального репозитория. Защитите теги
релизов и доступ к репозиторию.

Wheel включает весь канонический каталог `skills/project-memory/`.
`build_installer.py` создаёт из этого wheel детерминированный
`richi-installer.pyz`, использующий только стандартную библиотеку, и отдельный
файл SHA256. Workflow публикует эти файлы и `install.sh` вместе с wheel и manifest.
Каждое тестовое задание релиза устанавливает точные архив и wheel в синтетический
домашний каталог без доступа к личным данным. Публичный URL установки одной
командой работает только после публикации такого релиза.
