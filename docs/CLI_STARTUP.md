# Запуск CLI: гипотеза и протокол проверки

Протокол зафиксирован 16 октября 2026 перед сравнением candidate с baseline
`3b8d380` из main после PR #8. Область изменения — отложенные импорты
`tempfile` и `subprocess` в трёх модулях `richi_launcher`: `config`, `runtime`
и `workspaces`. Ниже сохранён исходный протокол и результаты сравнения.
Baseline-установка взята из `39fb95eb406fe8f5024423e222743717a977cd96`:
её production-код совпадает с squash merge `3b8d380098b9e809ead8a0cce566c66abf93e10f`.
Хеши установленных файлов и исходников проверяются измерителем.

## Наблюдаемая проблема и гипотеза

После отбора кандидатов recall обычный CLI всё ещё занимает около 300 мс.
В исходном локальном профиле медианы пяти обычных запусков составляли
289–342 мс. На корпусе с 10000 фоновыми entries отдельный инструментированный
вызов `recall` занимал 22–39 мс inclusive; заметная работа оставалась в
импортах, компиляции исходников и построении argparse. Проверка хеша release
в одном профиле занимала около 1,3 мс: этот замер не обосновывает её удаление.

Гипотеза: обычное чтение может не импортировать заранее библиотеки, нужные
для записи конфигурации/реестра или preflight. Перенос импорта к месту
использования уменьшит лишнюю работу запуска, сохранив поведение команд.
В dev `tempfile` по-прежнему нужен для свежего pycache prefix; эту защиту
нельзя убирать ради времени. Проверка runtime, выбор workspace, блокировки,
атомарная запись конфигурации и алгоритм recall остаются прежними.

Профиль служит основанием для гипотезы, а не измерением ускорения. cProfile
меняет время; cumulative-вызовы вложены и не складываются. Его обёртка заранее
импортирует собственную инфраструктуру, `json` и `pathlib`; запуск процесса,
exec и завершение также не полностью входят в профили. Поэтому нельзя
вычитать времена профиля из обычного wall time или выводить точную долю
startup. Линейный обход метаданных recall остаётся отдельной работой.

## Парное сравнение

1. Использовать неизменённые
   [runner](https://github.com/Hidanio/Richi/blob/ff966896ec9c28497430ec18b2c39706ee86d5ab/evals/evaluate_memory_growth.py)
   и [fixture PR #7](https://github.com/Hidanio/Richi/blob/ff966896ec9c28497430ec18b2c39706ee86d5ab/evals/memory_growth_cases.json)
   как внешний источник синтетических корпусов и фиксированных запросов.
   Исходные ожидания и raw baseline не переписывать; включение PR #7 в main
   не является условием эксперимента.
2. Установить baseline и candidate обычными пакетами в отдельные venv одного
   Python. Зафиксировать версии и хеши launcher/runtime, runner и fixture.
   Dev должен указывать на соответствующий зафиксированный checkout.
   Изменение launcher требует переустановки fixed package даже при `dev=true`:
   одного `git pull` или перезагрузки `src/richi` для применения недостаточно.
3. Матрица: background 100/10000 × `current-id`/`crowded-lexical` × release/dev,
   всего восемь условий. Details/history — 0; полных текущих entries —
   106/10006, entities — 0. Использовать одинаковые закрытые seed-копии,
   corpus hashes, `limit=8` и normal budget 16000. HOME/config/chat окружение
   изолировать от пользователя; рабочую память и настройки не переключать.
4. После одного нетаймируемого прогрева каждой пары variant/condition собрать
   девять пар на условие: 144 обычных CLI-запуска последовательно. В каждом
   раунде сдвигать порядок условий и чередовать baseline→candidate с обратным
   порядком. Сохранять сырые времена, median/p95 по вариантам и парные дельты.
   Генерация, seed, разбор JSON и проверки не входят в wall time команды.
5. Сравнить полный обычный JSON: refs, порядок, источники, состояния, read-more,
   ограничения и бюджет. Диагностику с `--expect` и бюджетом 100000 запускать
   отдельно от тайминга; сравнить counters и outcome. Проверить неизменность
   базы и непустого WAL; пустой и отсутствующий WAL эквивалентны, SHM исключён.
   Прежний пропуск выбранной цели широкого запроса учесть как quality miss,
   не менять oracle и не трактовать остальные совпадения как нерелевантные.
6. Отдельным профилем проверить исчезновение целевых импортов на обычном пути,
   сохранив исходные `.prof`. Пройти тесты launcher/config/workspaces,
   полную unittest suite и acceptance recall по правилам
   [EVALUATION.md](../skills/project-memory/references/EVALUATION.md).
   Особое внимание — путям записи и preflight, которые теперь импортируют
   библиотеки по месту, а также свежести кода в dev.

Приёмка требует прежнего поведения и фактического уменьшения лишних импортов;
временной эффект публикуется по всем восьми условиям, включая замедления.
Последовательный парный порядок уменьшает влияние дрейфа, но не контролирует
нагрузку хоста. Кеши не сбрасываются, холодный старт не измеряется; p95 девяти
повторов равен максимуму и не оценивает надёжно хвост распределения. Эти замеры
не задают SLA или временной CI gate, не измеряют рост entities/истории/деталей
одной Jira и не обещают ускорение всех команд или версий Python.

## Проверки

Полная unittest suite: 565 тестов за 580,125 с, `OK (skipped=1)` —
564 passed и один пропущен. Acceptance recall: 7/7, база не изменилась.
Эти проверки подтверждают прохождение сценариев поведения; временной эффект
проверяется отдельным парным экспериментом по протоколу выше.

## Результаты парного эксперимента

[Raw JSON](../evals/results/cli-startup-before-after-2026-10-16.json) получен
16 октября 2026, 20:32:19–20:33:36 по Москве, на macOS arm64, Python 3.9.6,
SQLite 3.43.2. Runner выполнил 144 обычных вызова и проверил равенство полных
обычных и диагностических JSON, неизменность кода и базы: нарушений нет.
Четыре условия `crowded-lexical` сохранили прежний quality miss; успешное
завершение здесь означает сохранение поведения, а не идеальное качество поиска.

| Режим | Background | Запрос | Медиана до, мс | Медиана после, мс | Медиана парной Δ, мс |
| --- | ---: | --- | ---: | ---: | ---: |
| release | 100 | current-id | 347,07 | 261,50 | −85,85 |
| release | 100 | crowded-lexical | 289,04 | 265,20 | −20,45 |
| dev | 100 | current-id | 307,61 | 275,72 | −34,56 |
| dev | 100 | crowded-lexical | 284,96 | 286,47 | +2,19 |
| release | 10000 | current-id | 364,16 | 281,28 | −37,61 |
| release | 10000 | crowded-lexical | 310,97 | 287,82 | −21,58 |
| dev | 10000 | current-id | 370,28 | 294,88 | −13,79 |
| dev | 10000 | crowded-lexical | 305,04 | 304,51 | −3,82 |

Парная Δ — `candidate_ms − baseline_ms` внутри пары; её медиана не равна
разности медиан вариантов. Например, release/current-id/10000 даёт −37,61 мс
по парам при разности медиан −82,88 мс; dev/current-id/10000 — −13,79 против
−75,40 мс. Нагрузка хоста не контролировалась, разброс велик. Равномерного
ускорения нет: медиана dev/crowded-lexical/100 выросла на 0,5%, а при 10000
почти не изменилась (−0,2%). Из этих данных нельзя вывести фиксированный
процент ускорения или SLA.

Отдельные профили при 10000 подтвердили уменьшение целевых импортов: в release
launcher исчезли `tempfile`, `shutil`, `subprocess`; в dev исчез `subprocess`,
а `tempfile`/`shutil` остались для свежего pycache prefix. В дочернем runtime
обоих режимов исчез `tempfile`; `shutil` остался нужен argparse. Это подтверждает
изменение выполненной работы, но времена профиля не подменяют обычные замеры.

Первая попытка остановилась при подготовке, до таймируемых запусков: местный
SQLite/VFS не открывал свежую копию WAL-mode базы через `mode=ro` без sidecars.
Harness теперь выполняет один setup `mode=rw SELECT` на синтетической копии,
явно закрывает соединение и проверяет равенство SHA основной базы seed-копии;
только затем фиксирует read-only digest. Это исправление подготовки эксперимента,
не результат о production или производительности; инварианты не ослаблены.

## Воспроизведение

[Runner](../evals/evaluate_cli_startup.py) требует внешние helper/fixture именно
из `ff966896ec9c28497430ec18b2c39706ee86d5ab` и отказывается перезаписывать output.
SHA-256 использованных файлов:

| Файл | SHA-256 |
| --- | --- |
| evaluate_cli_startup.py | `9d16603ec58d46873354c5f7616ef21bacbf5c216f3849489ac3afa4feaf7762` |
| evaluate_memory_growth.py | `013ea13bef2a127ed0c631454cc0615e744a333d153a633ddcd2c4895cccc908` |
| memory_growth_cases.json | `a38d6fdad925a1f2045b13faad83a611bbe01ed274fba42b0888772df4b60e31` |

Полные хеши installed/source launcher и runtime, пути venv, выбор режима,
сырые пары и профильные таблицы сохранены в JSON. Подготовьте обычные установки
baseline и candidate одного Python из соответствующих checkout, затем укажите
их абсолютные пути и новый output. Пример вызова из checkout candidate:

```sh
/path/to/baseline-venv/bin/python -I -B evals/evaluate_cli_startup.py \
  --baseline-python /path/to/baseline-venv/bin/python \
  --candidate-python /path/to/candidate-venv/bin/python \
  --baseline-source /path/to/baseline-checkout \
  --candidate-source /path/to/candidate-checkout \
  --growth-evals /path/to/ff96689-checkout/evals \
  --repeats 9 --output /tmp/cli-startup-new.json
```
