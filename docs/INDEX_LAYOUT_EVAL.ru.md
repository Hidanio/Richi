# Сравнение структуры производного поискового индекса

[English](INDEX_LAYOUT_EVAL.md) | Русский

Структура v2 уменьшила дополнительное выделение SQLite с **10,387,456 до 4,857,856
байт (53.2%)** на публичной синтетической фикстуре из 10,000 entries и 1,000 entities.
Канонические строки знаний не изменились. Совпали все 38 сравнений наборов
кандидатов entry/entity и все 14 обычных ответов recall; последние также имели
идентичный сериализованный JSON. Это эксперимент со структурой индекса,
отдельный от оценок установленного пакета и рабочих сценариев агента.

[Машиночитаемый отчёт](../evals/results/index-layout-2026-10-25.json)
содержит хеши модулей и фикстуры, выделение `dbstat` по объектам, медианы запросов,
замеры записи и хеши обычных ответов без измерения времени. Старый модуль взят из
`84e1b6c3684dd17ca7385d511fcd1b408d11a68a`; его байты совпадают с первоначально
измеренным модулем `c130086`, что независимо проверено по SHA-256. Оба модуля
индекса работали в одном runtime из исходников, чтобы изолировать реализацию
индекса. Это не два измерения установленных пакетов.

<a id="where-the-bytes-went"></a>
## На что расходовались байты

Старый первичный ключ `WITHOUT ROWID` содержал четыре текстовых значения:
семейство, поле, ключ и собственный ID. Вторичный индекс неявно повторял
оставшиеся столбцы первичного ключа, дублируя почти всю строку. V2 использует
небольшие коды полей и стабильное отображение записей на целые числа. Это
отображение владеет собственными целочисленными идентификаторами и не зависит
от неявных rowid авторитетных таблиц. Полные ID разрешаются по целому запросу
и варианту с одним удалённым префиксом семейства: неоднозначность собственного
и полного ID сохраняется без хранения дублирующих ключей.

| Объект SQLite | Выделено байт V1 | Выделено байт V2 |
|---|---:|---:|
| Ключи поиска | 5,029,888 | 2,011,136 |
| Поиск по записи | 4,857,856 | 1,748,992 |
| Отображение записей | 0 | 282,624 |
| Индекс идентичности отображения записей | 0 | 315,392 |
| Три индекса state/kind/work-state | 491,520 | 491,520 |
| Изменённые записи | 4,096 | 4,096 |
| Дополнительное выделение под схему | 4,096 | 4,096 |
| **Всего дополнительного выделения** | **10,387,456** | **4,857,856** |

Вторичный индекс поиска строится после первоначального заполнения, что уменьшает
фрагментацию и обслуживание при каждой вставке. Число строк поиска сократилось
с 98,894 до 87,894; объём сохранённого текста ключей — с 1,104,860 до 862,883 байт.
Ни один показатель сам по себе не измеряет полное физическое хранение. Источники
и история по-прежнему исключены.

Отдельный прототип со словарём и списками вхождений экономил лишь ещё 139,264 байт
относительно простого прототипа с отображением (около 3%), добавляя join и очистку
ключей без владельца. Этот вариант не принят. Финальная структура с отображением
также выиграла от массового построения вторичного индекса, поэтому размеры
прототипов не являются результатами финальной реализации.

<a id="timing-observations-and-limits"></a>
## Наблюдения времени и ограничения

| Измерение | V1 | V2 |
|---|---:|---:|
| Одно построение внутри процесса | 463.17 ms | 281.83 ms |
| Медиана p50 для 38 случаев поиска кандидатов | 0.0512 ms | 0.0556 ms |
| Обновление метаданных entry, p50, 20 записей | 0.2596 ms | 0.2456 ms |
| Обновление summary entry, p50, 20 записей | 0.2499 ms | 0.2341 ms |

Join с отображением записей немного удорожает поиск: широкие случаи entity
замедлились на 2–5%, максимум на 0.019 ms в этой выборке. Поэтому структуру нужно
оценивать по полной задержке поиска наряду с использованием диска. Таблица
не заявляет ускорения поиска или стабильной хвостовой задержки в production.

Вызовы поиска чередовали варианты в 40 повторах; исходный диагностический отчёт
сохранил только их p50. Построение выполнялось один раз для каждого варианта,
сначала v1, затем v2. Записи выполнялись 20 раз каждого вида, сначала v1, затем v2;
сохранены отдельные замеры. Кеши не сбрасывались, доверительный интервал и контроль
параллельной нагрузки отсутствовали. Построение включает вычисление производного
статуса, но исключает запуск процесса; записи используют обычные API entry и
включают обновления истории. Измеренные правки текста entry меняют summary,
индексируемые FTS, но не являющиеся ключами маршрутизации. Стоимость записи текста
entity требует отдельного измерения. Байты описывают свежие построения на
эквивалентных уплотнённых синтетических копиях: это выделенные страницы, а не
пиковый WAL или автоматически освобождённое место на диске.

Изменения только метаданных или свидетельств больше не помечают ключи
маршрутизации изменёнными и не перестраивают их. Уже изменённые записи всё ещё
обновляются; слишком большие записи остаются на пути сканирования до изменения
значимого поля или явной повторной попытки построения. Тесты покрывают оба случая,
rollback, старые SQL-writers, неоднозначность ID, изменения rowid источника,
отсутствующие индексы и конфликты зарезервированных имён.

<a id="compatibility-and-reproduction"></a>
## Совместимость и воспроизведение

`search-index build` явно обновляет производную версию 1 до 2. Чтения никогда
этого не делают. Старые читатели версии 1 видят неподдерживаемую производную
версию и возвращаются к сканированию; фиксированный старый reader проверен на
хранилище v2. `user_version` приложения остаётся 2. После обновления старые
страницы могут остаться в freelist SQLite; измеренное сокращение не означает
немедленного уменьшения существующего файла базы. Автоматический VACUUM не добавлен.

Публичный [сценарий воспроизведения](../evals/evaluate_index_layout.py) создаёт
только временные синтетические базы и никогда не принимает пользовательскую базу.
Запускайте его из этого checkout в Python-окружении с тестовыми зависимостями
Richi и поддержкой SQLite `dbstat`. В истории Git checkout должна присутствовать
фиксированная старая ревизия; реализация candidate и синтетическая фикстура
загружаются из исходников этого checkout:

```sh
/path/to/python evals/evaluate_index_layout.py \
  --checkout /path/to/Richi \
  --old-revision 84e1b6c3684dd17ca7385d511fcd1b408d11a68a \
  --output /path/to/new-layout-report.json
```

Опубликованные числа сохраняют исходные диагностические замеры; публикация
сценария не перезапускала и не заменяла их. Скрипт сохранён после первого
измерения и побайтно совпадает с локальным `reproduce.py`. В отличие от исходной
диагностики, будущие запуски также сохраняют сырые замеры поиска. Исходные
наблюдения остаются локально в `/private/tmp/richi-indexed-v2-layout-20261025/`;
для воспроизведения сравнения этот каталог не нужен. Равенство обычных ответов
проверялось отдельно, без новых замеров времени. Идентичные сериализованные
ответы означают одинаковое число токенов ответа при фиксированном токенизаторе;
само это изменение не заявляет сокращения токенов ответа или ошибок агента.
