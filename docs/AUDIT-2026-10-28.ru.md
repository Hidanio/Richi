## Приведённые в порядок границы

- CLI-декларации вынесены из `memory.py` в `cli_parser.py`. Совместимый вход
  `memory.parser()` сохранён. Разбор аргументов не импортирует тяжёлые реализации
  Git, поиска или карты. Парсер получает только необходимые типы/валидаторы.
- Правила принадлежности пути проекту вынесены в `projects.match_project`.
  `status` больше не вызывает метод чужого класса, подставляя собственный объект
  вместо `self`. У status и discovery сохранены собственные бюджеты и кеши,
  а правила выбора проекта общие.
- `sources related` использует общий валидатор Git-пути вместо второго набора
  почти одинаковых условий.
- Git и graph HTTP workers используют один механизм ограниченного чтения,
  сохраняя отдельные лимиты, протоколы и обработку ошибок.

Схема SQLite и форматы записей не меняются. История, optimistic concurrency,
явная миграция и изоляция workspace сохраняются. Идемпотентный `unchanged` со
старым `expected_updated_at` — существующий документированный контракт, а не
найденная ошибка.

Дополнительное независимое ревью core не выявило нового подтверждённого риска
порчи данных. CLI batch использует `BEGIN IMMEDIATE`; записи, membership,
history/events и FTS triggers входят в одну транзакцию. CAS проверяется внутри
неё, replay связан с хешем payload. Миграция выполняет SQL без implicit commit,
проверяет FK/integrity и меняет `user_version` последним. Это проверенные
механизмы и покрытые тестами сценарии, а не гарантия для произвольной повреждённой
базы или сторонней прямой записи в SQLite.

## Оставшиеся проблемы и порядок дальнейшей работы

### P2: нормализация Unicode расходится с FTS

Воспроизводимый случай: подтверждённая entry `tree` с title `берёза контекст`,
summary `Recorded evidence.`, пустыми aliases и источником `fixture://tree`.
Оба запроса `recall береза` и `recall берёза` не возвращают запись.
`--expect entry:tree --explain` показывает `fts_not_shortlisted`.
Повторно подтверждено после интеграции `6729d4c` на новой синтетической базе
schema 2 / FTS5: новый индекс не устраняет расхождение, точный `entry:tree`
возвращает запись.

`recall.normalize()` сводит `ё` к `е`, но FTS индексирует исходный текст.
Кандидат теряется до Python scoring. Это проблема полноты поиска; отсутствие
результата не доказывает отсутствие знания. Чтение по точному ID работает.

Следующий шаг: согласовать нормализацию индекса и запроса, определить явный
rebuild/migration существующих индексов и проверить FTS/scan parity на Unicode.
Нельзя исправлять это только перебором вариантов запроса: число комбинаций
растёт, а candidate cap вносит дополнительное смещение. Не следует молча
перестраивать пользовательские базы при обычном запуске CLI.

### P3: три реализации атомарной записи JSON и цикл config/workspaces

`config`, `workspaces` и `installation` повторяют temp-file/replace/fsync;
`chats` импортирует writer из доменного модуля workspaces. При этом реализации
различаются: сохранение mode, fsync каталога, восстановление после ошибки уже
после `replace`. `config` и `workspaces` связаны обратными lazy imports.

Следующий шаг: выделить независимые path/JSON primitives с явными политиками
и контрактом ошибки после replace. Простая замена всех вызовов одним helper
опасна: cleanup создания workspace и переключение установленной версии имеют
разные транзакционные обязательства.

### P3: несколько алгоритмов ограничения ответа

`compact`, `task_brief`, `git_impact` и diagnostics по-разному ограничивают
ответ. У них различаются состав результата и обязательные свидетельства.
Следующий шаг: общий расчёт размера сериализованного ответа и явный контракт
сохранения связки «карточка + основание», со специализированным отбором для
каждой команды. Не заменять разные политики универсальным обрезанием JSON.

### P3: размер объектов внутри graph worker

Новый лимит вывода защищает буферы HTTP-сервера. Сам дочерний процесс сначала
материализует граф с полными карточками; количество узлов/рёбер ограничено,
суммарный размер их содержимого — нет. Следующий шаг: отдельный бюджет экспорта
или потоковая сериализация с явной неполнотой. Это остаточный риск ресурсов,
не утверждение о воспроизведённом падении на пользовательских данных.

### Границы, которые нужно сохранить

- Bootstrap выбирает исправную версию до импорта launcher. Общий парсер с
  потенциально повреждённым current runtime разрушит аварийный откат.
- Launcher владеет workspace/chat/config и выбором runtime; runtime владеет
  знаниями и прикладными командами. Dev-режим не подменяет launcher.
- Проекты, entry membership и legacy relations уже проецируются в граф через
  registry/view. Это совместимость и целостность связей, а не основание
  создавать вторые изменяемые копии тех же данных.
- Автоматический ingest, семантический поиск и новые слои доменной модели не
  нужны для исправления найденных ошибок.

Среда финального прогона: macOS, Python 3.9; Linux и Python 3.12 в этой сессии
не запускались. Публичный recall eval проверяет ограниченную синтетическую
выборку и не покрывает весь Unicode или все размеры графа. В том числе 7/7
не отменяет зафиксированную выше проблему `е/ё`.

Исправление bootstrap начнёт действовать в постоянной установке после
переустановки launcher. Изменения runtime подхватываются dev-режимом при следующем
вызове. Этот аудит не заменяет постоянную установку и не обновляет релизы.
