# Обновления из GitHub Releases

[English](UPDATES.md) | Русский

Richi устанавливается в отдельное окружение Python. После первоначальной
установки опубликованные стабильные версии можно получать командами:

```sh
richi update check
richi update apply
richi update rollback
```

`check` только проверяет официальный репозиторий `Hidanio/Richi` и показывает
текущую/предыдущую установленную версию. `apply` скачивает последний стабильный
релиз. Для конкретного релиза используйте `--version X.Y.Z` у `check` или `apply`.
Draft и prerelease не устанавливаются. Если релизов ещё нет, результат —
`no_release`; наличие кода в основной ветке не означает наличие релиза.
Сетевые ошибки не меняют установленный код.

Обновляется **установка целиком**, для всех использующих её workspace.
Команды обновления не принимают `-w`, `--config`, `--db` и `--project-path`,
не читают базы и не требуют выбора workspace в новом чате.
Существующие привязки чатов, настройки `dev`, пути исходников, SQLite и
Git-снимки остаются прежними. При включённом dev команды памяти продолжают
использовать исходники, а управляемые ссылки skill остаются на checkout;
`dev false` выбирает установленный релиз и его skill. Сломанный dev не блокирует
проверку и установку релиза. Релизы до 1.1.0 включительно не умеют обслуживать
ссылки skill на checkout: перед откатом на такой релиз выполните
`richi config set dev false` ([что переключает dev](INSTALLATION.ru.md#что-переключает-dev)).

<a id="installation-and-rollback"></a>
## Установка и откат

Обновлятор проверяет версию, протокол запуска, поддерживаемые схемы, размер
и SHA256 wheel, затем создаёт отдельное окружение для кандидата. Установка
использует только проверенный wheel, без загрузки зависимостей из PyPI.
Импорты и версия кандидата проверяются отдельным процессом до переключения.
После успешной проверки указатель текущей версии меняется атомарно.
Неудачный кандидат удаляется; текущая версия остаётся на месте.

`rollback` переключает на предыдущую версию без сети. После отката версии
меняются местами, так что повторный откат возвращает прежнюю текущую версию.
Downgrade через `apply` запрещён: для этого есть явный откат. Установка из
checkout не имеет подтверждённой идентичности опубликованного wheel, поэтому
релиз с таким же номером можно установить один раз; совпадение номера само по
себе не доказывает совпадение сборки.

`check` возвращает `incompatible_release` и `can_apply: false`, если релиз несовместим
с текущим Python, протоколом обновлятора или полями манифеста первого протокола.
Если wheel уже проверенного установленного релиза заменён другим файлом с тем же
номером версии, результат — `release_changed`, установка отклоняется. Для
исправленной сборки нужна новая версия. Фоновые проверки без автоматической установки
сообщают те же причины и не предлагают команду установки для заблокированного релиза.
Поддерживаемые релизом схемы базы известны только из его самопроверки, после
загрузки: релиз, который потерял бы поддерживаемую схему, отклоняется при установке,
а его подготовленная копия удаляется.

Обновление не выполняет миграцию базы. Каждый релиз первого протокола сохраняет
поля манифеста, которые принимают обновляторы до 1.0.1 включительно:
`database_schemas` всегда `[1, 2]`, а `map_schema` и `memory.VERSION` релиза всегда
равны 2. Какие схемы релиз поддерживает на самом деле, определяется его
самопроверкой (`memory.SUPPORTED_VERSIONS`) и сохраняется для каждого
установленного поколения. Поэтому любая управляемая установка, в том числе на 1.0.1,
переходит на последний релиз первого протокола одним `richi update apply` (или
автоматической установкой), сколько бы релизов ни было пропущено. Для мейнтейнеров:
[контракт релизов](RELEASING.ru.md#protocol-1-release-contract).

Текущий runtime поддерживает схемы базы 1, 2 и 3. Новые хранилища создаются сразу со
схемой 3; существующим для карточек инструментов нужна явная миграция. Откат runtime
не понижает версию хранилища, а старый runtime может его не читать. Сохраните backup
до миграции. Подробнее — [миграция графа](../skills/project-memory/references/GRAPH.ru.md).

<a id="schema-support"></a>
Менеджер сохраняет проверенный набор поддерживаемых схем базы для каждого
установленного поколения. Активация и откат запрещают уменьшать этот набор, в том
числе переходить с поддержки 1/2/3 на 1/2. Консервативная проверка не открывает
базы workspace и действует, даже если ни одна база не мигрирована. Bootstrap,
установленный версией 1.1.0 или новее, тоже проверяет совместимость до передачи
отката предыдущему менеджеру, используя сохранённые метаданные даже при повреждении
текущего пакета; установки, начатые на 1.0.x, сохраняют исходный bootstrap, который
этого не делает. Откат между поколениями с совместимой поддержкой схем остаётся
доступен. При отказе сообщение объясняет, что откат пакета не откатывает базы;
выберите совместимый релиз.

Обновляторы до 1.0.1 включительно выполняют откат сами, без этой проверки. Если
хранилище на схеме 3 (мигрировано или создано через `init` на 1.1.0 и новее), а вы
откатились на 1.0.1, она откажется открывать это хранилище и ничего в нём не
изменит; выполните `richi update apply`, чтобы вернуться на последний релиз. После
подключения Claude Code 1.0.1 сама откажет в откате, потому что не умеет обслуживать
эту интеграцию. Если была включена автоматическая установка, такой отказ оставит её
на паузе; возобновите её через `richi update auto enable --install`. Следующие
релизы при неудачном откате восстанавливают прежнее состояние паузы.

<a id="updater-protocols"></a>
## Протоколы обновлятора

Все релизы пока используют протокол обновлятора 1. Релиз, которому нужен более
новый протокол, отображается как `incompatible_release` (или отклоняется при чтении
манифеста), и ничего не устанавливается и не меняется; как перейти на него,
описывается в примечаниях к такому релизу. Мейнтейнеры сохраняют возможность
обновления установок первого протокола, как описано в
[контракте релизов](RELEASING.ru.md#protocol-1-release-contract).

<a id="version-retention"></a>
## Сколько версий хранится

Постоянно хранятся текущая и одна предыдущая версия. Во время установки
временно существует кандидат. У каждой работающей команды, карты и её
дочерних процессов есть блокировка используемой версии: очистка не удаляет
код, которым они ещё пользуются. Такая отложенная версия может временно
увеличить число каталогов. После завершения процессов очистка выполняется
при следующем обновлении, откате или явно:

```sh
richi update cleanup
```

Результат показывает удалённые и отложенные версии и ошибки очистки.
`check` ничего не удаляет. Исходное окружение сохраняет Python и небольшой
постоянный модуль запуска; после вытеснения исходной версии её полный код
также удаляется. Это инфраструктура запуска, а не третья полная версия Richi.

Состояние хранится в платформенном каталоге Richi, в `installations/`, отдельно
для каждого исходного окружения Python. Пути отображаются в `update check`.
Настройки конкретного workspace не определяют расположение установленного кода.
Не перемещайте вручную управляемые окружения и не редактируйте указатели версий.

<a id="running-maps-and-the-initial-transition"></a>
## Работающая карта и первоначальный переход

Новые вызовы CLI получают новую версию сразу. Работающая карта тоже следует за
установкой: после `update apply`, автоустановки и `update rollback` ручные шаги не
нужны. Достаточно обновить открытую вкладку браузера: адрес не меняется.

- Карта, запущенная этим или более новым релизом, сама перезапускается на ставшей
  текущей версии, сохраняя процесс и адрес; `richi map serve` остаётся в своём
  терминале. Сразу после активации обновлятор просит об этом найденные карты:
  зарегистрированные управляемой установкой и работающие на портах по умолчанию
  (8765 и десять следующих или из `RICHI_PORT`). Он дожидается их и сообщает
  результат в поле `maps` JSON-ответа: по записи на карту с `url`, `pid`,
  `status` и `version`:
  - `restarted`, с `from_version`: карта работает на активированной версии;
  - `current`: карта уже работала на ней, например перешла сама;
  - `restart_required`, с `from_version` и `error`: старая карта, см. ниже;
  - `pending` или `failed`, с `from_version` и `error`: карту попросили
    перейти, но она не перешла, например осталась на своей версии (см. следующий
    пункт).

  В результатах активации есть и `restart_maps_required`: он равен `true`, пока
  найденная карта работает на старой версии. Если поиск карт не удался,
  обновление всё равно остаётся применённым: тогда `maps` пуст, `maps_error`
  объясняет причину, а `restart_maps_required` равен `true`. Другие команды
  обновления (`check`, `status`, `cleanup`) карты не сообщают. Если текущую версию
  меняет более старый менеджер, например откат силами 1.1.0 или более ранней
  версии, карта замечает это и примерно через пять секунд переходит сама.
- Прежде чем перейти, карта один раз запускает ставший текущим релиз через точку
  входа установки со своим выбором хранилища (`richi --version`) и проверяет, что
  релиз полон и заявляет поддержку схемы её базы. Иначе карта остаётся на своей
  версии, один раз записывает причину в журнал и позже пробует снова. Так бывает,
  например, после отката силами самой 1.0.1, когда база уже на схеме 3: 1.0.1 не
  может открыть такую базу, поэтому более новая карта продолжает её показывать,
  пока установка не изменится снова. Просьба о перезапуске, когда карта уже
  работает на текущей версии, игнорируется.
- Карта, запущенная 1.1.0 или более ранней версией, переходить не умеет. После
  обновления таким менеджером первая команда работы со знаниями на новой версии,
  например `richi --version` или `richi project list`, один раз ищет карты:
  зарегистрированные установкой и на портах, которые `richi map` использовал бы
  для workspace этой команды (настроенный и десять следующих). `status`, `chat`,
  `config`, `workspace`, `use`, `update`, `setup`, `agents` и `map` карты не ищут.
  Команда никогда не ждёт карту: новые карты она просит перейти, а старую карту
  в фоне останавливает и запускает заново на новой версии на том же порту. Такую
  замену запускает только команда из терминала без идентификатора чата. Команда
  агента (у неё есть идентификатор чата, и она может работать в песочнице),
  скрипта или планировщика только просит новые карты перейти; старые карты
  заменит следующая команда из терминала или `richi map`. Старую карту, которая
  сама работает в терминале (`richi map serve`), так не заменить: остановите её
  там и запустите снова либо выполните `richi map restart`. Каждый диапазон
  портов просматривается один раз на версию, поэтому команда для порта другого
  workspace просматривает и его диапазон.
- `richi map` поддерживает карту своего workspace на текущей версии по тому же
  адресу. Карту той же установки он просит перейти на месте; карту, запущенную
  1.1.0 или более ранней версией, либо карту из другого окружения установки
  заменяет. Пока карта перезапускается, он ждёт её, а не занимает её порт.
  Поэтому ярлык на рабочем столе, запускающий `richi map`, всегда открывает
  текущую версию. Сначала проверяется новая версия, и там, где нельзя открыть
  локальный порт, работающая карта не останавливается. Если одну базу
  обслуживают две установки, карта достаётся той, чей `richi map` запускался
  последним.

Явно остановить или перезапустить карту выбранного workspace:

```sh
richi map stop
richi map restart
richi map restart --no-open
```

`stop` сообщает `stopped` (с `pid`, `version` и признаком `exited`, завершился ли
процесс) или `not_running`. Если первый порт занят картой другого workspace или
другой программой, у `not_running` есть пояснение `note`; ни то, ни другое не
трогается. Если карту этого workspace остановить нельзя, `stop` с кодом
завершения 1 сообщает `refused` с причиной `reason`: `unverified_process`,
`foreign_user`, `not_permitted` (окружению нельзя посылать сигналы этому
процессу, например в песочнице), `process_exited`, `changed` (карта тем временем
изменилась; повторите команду) или `timeout`. `restart` останавливает карту и
запускает текущую версию на том же адресе, а если карта не запущена — просто
запускает её; как и `richi map`, открывает браузер, если не указан `--no-open`.

Карта опознаётся только по ответу `/api/health`: приложению, сообщённому PID
процесса и runtime. Перед любым сигналом Richi проверяет, что этот процесс
принадлежит текущему пользователю и выполняет сервер карты Richi ровно с этим
runtime. Чужие программы, непроверяемые процессы и карты других workspace никогда
не останавливаются. Остановка отправляет только `SIGTERM`: карта закрывает порт
и завершается. Просьба о переходе — это `SIGUSR1`, и её получают только карты,
заявляющие возможность `installation_handoff`. Карта удерживает блокировку
старой версии, пока её код работает, поэтому очистка не удаляет используемый
код; освобождённые при переходе версии удаляет сам обновлятор либо следующий
`update cleanup`. Переход не читает данные workspace сверх того, что читает сама
карта (для проверки совместимости она читает номер схемы своей базы); обновлятор
по-прежнему не открывает базы и не читает конфигурацию workspace. Реестр
работающих карт хранится в `maps/` рядом с состоянием установки и появляется
только у управляемой установки.

При переходе со старой установки без этого обновлятора один раз установите
новый wheel в исходное выделенное окружение Python и перезапустите все старые
процессы Richi. Они ещё не умеют удерживать блокировки версии. После этого
обычные обновления выполняются через CLI. В управляемой установке используйте
`update apply`, а не переустановку пакета через pip поверх исходного окружения.

Обновлятор отказывается менять системный Python, editable-установку и окружение
с посторонними пакетами. Для такого случая создайте отдельное окружение по
[инструкции установки](INSTALLATION.ru.md). Проверить наличие релизов можно и без
поддержки управляемой установки.

Порядок публикации описан в [RELEASING.md](RELEASING.ru.md).

<a id="background-checks-and-installation-choice"></a>
## Фоновая проверка и выбор установки

Фоновая проверка и автоустановка изначально выключены. Чтобы только проверять
релизы по расписанию, зарегистрируйте задание пользователя в macOS LaunchAgent
или Linux systemd --user:

```sh
richi update auto enable --interval 6h
richi update auto status
```

Такой режим получает сведения о релизе, но не скачивает wheel и не меняет
установленную версию. Доступный релиз и команду его установки можно увидеть в
`auto status`. Пользователь сам решает, когда выполнить `richi update apply`
или `richi update apply --version X.Y.Z`. Кроме того, `richi chat current` сообщает
о более новом релизе, найденном последней проверкой, в поле `update`: значение берётся
из сохранённого результата, без обращения к сети. Агенты, следующие Project Memory,
выполняют эту команду в начале каждого чата, один раз упоминают обновление и никогда
не устанавливают его сами. Системные уведомления и кнопка установки в карте пока не реализованы.

Автоустановка — отдельная опция, **выключенная по умолчанию**. Включайте её,
только если хотите устанавливать подходящие релизы без отдельного подтверждения
каждой версии:

```sh
richi update auto enable --interval 6h --install
```

Без флага `--install` команда `enable` всегда выбирает только проверку, даже
если автоустановка была включена раньше. Старые настройки без явного поля
`auto_install: true` также разрешают только проверку. `auto status` показывает
отдельно `enabled` (расписание) и `auto_install` (разрешение установки).

```sh
# Выключить автоустановку, оставить проверку:
richi update auto enable --interval 6h
# Выключить весь фоновый режим и снять системное задание:
richi update auto disable
```

Интервал по умолчанию — 6 часов, допустимы целые минуты, часы и дни от `15m`
до `7d`. Системное задание просыпается каждые 15 минут; Python проверяет срок
следующей попытки и завершает вызов, если ещё рано. `enable` сбрасывает срок
и разрешает ближайшую проверку. Выключенный или спящий компьютер проверять
релизы не может: проверки продолжатся после возвращения пользовательского
сеанса. Постоянный процесс, Codex, LLM и токены для этого не нужны.

Для одной попытки по тем же правилам срока и выбранного режима:

```sh
richi update auto run
```

Команда не обходит отключение и не требует выбора workspace. Расписание
запускает постоянный Python исходной установки с очищенным окружением.
SQLite, настройки workspace и dev-исходники фоновый режим не меняет.

При временной сетевой ошибке повтор назначается через 15 минут, затем 30 минут
и далее с удвоением до выбранного интервала. Отсутствие опубликованных релизов —
штатный результат `no_release`.

<a id="safeguards-for-automatic-installation"></a>
## Защита при включённой автоустановке

Режим `--install` использует тот же проверенный wheel и атомарную установку,
что `update apply`. Работающие карты переходят на установленную версию так же, как
после `update apply`: они перезапускаются сами, поэтому фоновое задание не
становится их родительским процессом. Непрошедший проверку кандидат блокируется до более новой
версии или явного повторного включения. Одновременные попытки сериализуются;
ручная операция имеет приоритет перед ожидающей фоновой установкой.

`disable` сначала сохраняет отключение и снимает разрешение автоустановки,
затем удаляет системное задание. Если загрузка уже началась, финальная проверка
отменит переключение и удалит кандидата. Завершившееся до отключения обновление
остаётся установленным. Если удаление задания ОС не удалось, политика всё равно
остаётся отключённой; ошибка команды объяснит, что нужно исправить.

Ручной откат приостанавливает автоустановку, чтобы она не вернула отменённую
версию. Неожиданное изменение текущего поколения установки, включая ручное
применение другой версии или откат через старый запускатель, тоже вызывает
паузу автоустановки. Повторное `enable --install` подтверждает текущее состояние
и возобновляет её. Обычный `enable` возвращает к проверке без установки.
Проверки без автоустановки продолжают работать после ручного изменения версии.

`status` показывает реальную регистрацию задания ОС, срок следующей попытки,
последний результат, причину паузы и последние 20 событий. Состояние, политика и
журнал находятся рядом с метаданными установки в `installations/`; вывод фонового
процесса не накапливается в неограниченном файле. Для macOS нужен пользовательский
GUI-сеанс launchd, для Linux — работающий systemd user manager. Если такой
планировщик недоступен, включение завершается понятной ошибкой; явные команды
`update check` и `update apply` по-прежнему доступны.
