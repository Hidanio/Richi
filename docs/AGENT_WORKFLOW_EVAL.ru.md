# Оценка payload и контекста рабочих сценариев агента

[English](AGENT_WORKFLOW_EVAL.md) | Русский

Оценка измеряет заранее записанные локальные сценарии инструментов на синтетических
данных. Она не запускает языковую модель, не оценивает сгенерированные ответы и
не измеряет reasoning, production-точность, биллинг, эффективность кеша или полный
реальный разговор. Сравниваются фиксированная установленная baseline-версия
`b8a2a9aa889a7d65d433e985ca3f6a9d4cec4c60` и candidate. Прежние отчёты benchmark
поиска/индекса остаются неизменными.

<a id="what-is-compared"></a>
## Что сравнивается

Фикстура содержит 60 entries Atlas и 20 несвязанных entries Beacon с разными
knowledge/work states, двумя источниками на запись и условиями в конце каждого
summary длиной примерно 1,000 символов. Три confirmed-решения Atlas — необходимые
полные свидетельства для вопроса о размере пула. Пятьдесят текущих confirmed
entries Atlas составляют независимый oracle подсчёта, распределения и проекции.
Межпроектных связей нет, поэтому baseline `context --project atlas --limit 200`
перечисляет всю релевантную область. Superseded-записи не нужны для этих явно
ограниченных confirmed-состоянием задач.

Ожидаемые ответы получены от генератора фикстуры, а не парсера фильтров или
выдачи candidate. API baseline заполняет временную базу; SQLite backup создаёт
копию candidate. Построение индекса — явная подготовка вне сценариев чтения
агента. Требуемые полные записи должны совпадать с baseline full-get payload,
включая источники, условия, состояния и timestamps. Чтения сохраняют канонические
строки и физические отпечатки main/WAL.

| Сценарий | Существующие инструменты baseline | Инструменты candidate | Требуемый результат |
| --- | --- | --- | --- |
| Свидетельства в заданной области | Поиск строго в проекте; также discover + fetch | Прямой фильтрованный полный поиск; также фильтрованный discover + fetch | Те же три полные записи и источники |
| Число записей и распределение состояний | Полный контекст проекта + выборка/группировка | Точный count + facets | То же общее число и все группы, включая null |
| Положительная и отрицательная проверка существования | Полный context + явные предикаты | Два exists-запроса в области | True и false в сохранённой confirmed-области |
| Перечень метаданных | Полный context + проекция | Select запрошенных полей | Те же полные упорядоченные строки; тела намеренно исключены |
| Известные/отсутствующие ссылки | Fetch точных refs | Тот же fetch | Одна идентичная полная запись и один явный результат отсутствия |

Каждый релевантный baseline имеет вариант с сырым выводом и **работающий локальный
постпроцессор Python**. Весь фактически исполняемый код присутствует в записанных
аргументах команды. Он локально потребляет CLI JSON и показывает модели только
финальный результат: скрытые промежуточные записи учитываются как байты вне
модели и никогда не считаются видимым контекстом. Это более сильный baseline,
чем выгрузка всех записей в модель. Встроенный инструмент не считается заведомо
дешевле такого baseline.

Фильтрация/подсчёт в raw-baseline используют детерминированный oracle для
моделирования нужной выборки и арифметики; это не наблюдение агента, успешно
выполняющего эти шаги. Программный baseline действительно исполняет записанный
код. Наличие и размер программы измеряются; число reasoning-токенов или
инженерных попыток, потребовавшихся для её написания, неизвестно.

Основная проекция запрашивает до 200 строк и продолжает чтение, если этого
требует бюджет символов. Отдельная проверка курсора по семь строк подтверждает
точный порядок, отсутствие дублей/пропусков и полноту объединения. Её вызовы
имеют собственные transcript и метрики; они не добавляются и не исключаются
из основного сценария незаметно.

<a id="what-the-token-totals-include"></a>
## Что входит в суммы токенов

Для каждого варианта runner учитывает:

- Одинаковый prompt задачи и полный core skill соответствующего варианта.
- Только фактически загруженную документацию операций: фокусный baseline
  retrieval-документ или раздел search/context руководства CLI; candidate
  retrieval/query contract и, при использовании фильтров, начало руководства
  фильтров до семантики строковых предикатов включительно. Полная семантика
  запросов и пагинации загружается; одного parser help недостаточно.
- Каждый нормализованный аргумент команды и точный видимый ответ, включая
  форматирование JSON и завершающий перевод строки.
- Написанный вручную код программы, отдельно токенизированный для анализа;
  он уже включён в аргументы команды и **никогда не добавляется дважды**.
- Логические вызовы инструментов и заявленные раунды решений модели отдельно.

Два начальных пути candidate используют одинаковые прогрессивные операции
с данными/метаданными. `candidate_native` напрямую загружает известные руководства
операций, как разрешает core skill; `candidate_catalog` сначала перечисляет
релевантную группу возможностей и описывает выбранные команды, затем загружает
те же семантические руководства. Опциональные затраты discovery видны отдельно,
а не принудительно включены в каждое использование встроенного инструмента.
Группа каталога предопределена: модели, которой сначала нужно меню групп
верхнего уровня `capabilities list`, потребуется дополнительный вызов и контекст,
не измеренные в этом варианте каталога. Независимые чтения руководств делят
один раунд решений. Отдельный вариант прямого фильтрованного поиска решает
точно ограниченную задачу свидетельств с теми же full-search limit/output,
что baseline, учитывая раздел CLI search и контракт фильтров. Он сохраняет
точный oracle полных записей.

Аргументы инструментов используют документированную нормализованную оболочку:
`{"cmd":"richi ..."}`. Временные `--db`, конфигурация и home-селекторы,
нужные только harness, не являются видимыми агенту аргументами. Обрамление
инструментов провайдером и транспорт оркестрации не моделируются. `read_document`
— нормализованный адаптер чтения документации, не новая команда Richi.
Независимые описания известных схем и независимые query-операции могут делить
один раунд решений; зависимые вызовы остаются раздельными.

Сценарии — независимые задачи; сумма их cold totals не представляет один
измеренный разговор. Отдельно закодированный неэкранированный текст программы
имеет описательное назначение: его токенизация не обязана точно совпадать
с shell/JSON-экранированными подстроками аргументов.

И `o200k_base`, и `cl100k_base` токенизируют каждое видимое сообщение отдельно.
Токенизатор обязан использовать уже заполненный кеш; сетевые загрузки отключены.
Отчёты сохраняют точные аргументы команд, хеши/длины ответов, ответы и пошаговые
числа токенов, не дублируя каждое большое тело ответа.

Приводятся два представления:

1. **Сценарий с привязанным чатом без загруженных инструкций операции**:
   workspace и репозиторий уже выбраны/проверены. Задача начинается с prompt
   и загруженного core skill, затем загружает нужные контракты операций
   и выполняет записанные вызовы.
2. **Добавка только от операции**: новый prompt и вызовы операций с данными,
   без уже известных skill/контрактов. Это не утверждение, что существующий
   разговор или загруженная документация не занимают контекст.

`terminal_visible_tokens` — сумма независимо закодированных видимых сообщений.
`context_at_model_boundaries` содержит накопленный видимый ввод перед первым
решением и после каждого пакета ответов инструментов, включая возможность
финального ответа. Их сумма — иллюстративная модель накопленного ввода,
предполагающая повторную отправку видимой истории без compaction или скидок кеша.
Неизмеренные reasoning и текст финального ответа исключены. Дополнительный
префикс прежнего чата в P токенов добавляет P к финальному контексту и P,
умноженное на число границ решений, к накопленному вводу. Это **не измеренные
биллинговые токены**.

Payload данных по известным refs не должен сокращаться только из-за появления
новых команд. Агрегаты/проекции обоснованно исключают тела записей: эти задачи
запрашивают только метаданные, а не свидетельства для фактического вывода или
обновления. Усечение обязательных записей не засчитывается как выигрыш сценария
работы со свидетельствами.

<a id="reproduce"></a>
## Воспроизведение

Обычно установите обе версии в отдельные временные окружения и передайте
соответствующие деревья исходников с документами skill. Не используйте editable
установки или личные workspace. Скрипт не принимает существующую базу.

```sh
TIKTOKEN_CACHE_DIR=/path/to/prepopulated-cache \
  python3 evals/evaluate_agent_workflows.py \
  --baseline-python /path/to/baseline/bin/python \
  --candidate-python /path/to/candidate/bin/python \
  --baseline-source /path/to/frozen-b8a2a9a-source \
  --candidate-source /path/to/candidate-source \
  --tokenizer-python /path/to/tokenizer/bin/python \
  --output /path/to/new-report.json
```

`--baseline-only` — smoke-проверка контракта, не сравнительный результат.
Выходные файлы должны быть новыми. Заявлений о задержке нет: предмет оценки —
контракты возможностей и числа токенов, а не wall-clock time.

<a id="results"></a>
## Результаты

Опубликованный синтетический запуск: 2026-10-25, Python 3.9.6, SQLite 3.43.2,
tiktoken 0.14.0. [Полный машиночитаемый отчёт](../evals/results/agent-workflows-2026-10-25.json)
содержит хеши фикстуры/скрипта/runtime, точные нормализованные аргументы, хеши
ответов и результатов, числа компонентов, обе кодировки и каждый вариант.
Все 21 основных варианта прошли заранее заданные oracle. Отдельная восьмистраничная
проверка проекции вернула точное объединение и порядок 50 строк. Построение
индекса сохранило канонические строки; каждое записанное чтение сохранило
канонические и физические отпечатки main/WAL в обоих вариантах.

В каждой парной ячейке ниже указано **o200k / cl100k**. Сильный baseline —
исполненный Python pipeline, кроме неизменного встроенного fetch для известных
refs. Встроенный маршрут свидетельств использует прямой полный поиск со строгими
фильтрами; прогрессивный маршрут отражён отдельно.

Сокращение инструментами метаданных относительно сильного baseline — примерно
10–25%, а не около 94–99%, видимых при сравнении с сырой выгрузкой context.
Прямой фильтрованный поиск экономит около 11% относительно Python pipeline
свидетельств, сохраняя все три обязательные полные записи и по два источника
в каждой. Существующий fetch точных refs выполняет одинаковые операции с
данными и не даёт экономии в представлении «только операция».

Прогрессивный поиск свидетельств предлагает иной компромисс: существующий
discover + fetch стоит 5,102 / 5,111 токенов; фильтрованный discover + fetch —
1,965 / 1,974. Он выигрывает у того же прогрессивного baseline, но на этой
небольшой фикстуре дороже и Python pipeline полного поиска, и прямого
фильтрованного поиска. Он полезен, когда сначала необходимо выбрать refs;
это не универсально более дешёвый маршрут поиска entries.

экономию токенов в этих уже определённых задачах.

<a id="accumulated-visible-input"></a>
### Накопленный видимый ввод

Следующие числа o200k суммируют видимые префиксы на заявленных границах решений
модели. Это иллюстративная модель повторной отправки, не измерение биллинга;
обе кодировки и каждая граница доступны в отчёте.

| Сценарий | Cold baseline → native | Только операция baseline → native |
| --- | ---: | ---: |
| Полные свидетельства | 8,037 → 9,630 | 1,154 → 1,035 |
| Число + распределение | 7,203 → 7,820 | 320 → 251 |
| Положительное + отрицательное существование | 7,192 → 9,019 | 305 → 256 |
| Полный перечень метаданных | 7,948 → 8,531 | 1,069 → 966 |
| Известные + отсутствующие refs | 7,248 → 8,020 | 532 → 532 |

Cold cumulative input растёт во всех сравнениях с сильным baseline для o200k.
Для cl100k count/distribution и projection уменьшаются, остальные случаи растут.
Опциональные раунды каталога увеличивают ввод во всех случаях. Повторное
использование уже загруженных контрактов улучшает сравнение приращений, но
существующий разговор всё ещё занимает контекст и может отправляться повторно;
представление «только операция» явно исключает этот неизвестный префикс.

<a id="calls-code-and-limits"></a>
### Вызовы, код и ограничения

| Сценарий | Вызовы данных: baseline → native | Исполненный код анализа baseline, символы → native |
| --- | ---: | ---: |
| Полные свидетельства | 1 → 1 | 291 → 0 |
| Число + распределение | 1 → 2 | 400 → 0 |
| Положительное + отрицательное существование | 1 → 2 | 348 → 0 |
| Полный перечень метаданных | 1 → 1 | 308 → 0 |
| Известные + отсутствующие refs | 1 → 1 | 0 → 0 |

Независимые count/facets и два exists-вызова делят один раунд решений в заявленных
планах, хотя каждый остаётся отдельным логическим вызовом инструмента. Встроенные
инструменты устраняют эти рукописные постпроцессоры, но не необходимость выбрать
область, поля, предикаты или стратегию продолжения. Стоимость написания/отладки
кода не измерялась. Агрегаты/проекции намеренно исключают массивы источников
и тела свидетельств; задачи полных свидетельств этого не делают.

Фикстура покрывает метаданные entries и небольшую полную проектную область.
Она не демонстрирует самостоятельный выбор правильного сценария агентом,
аналитику entities, согласованный снимок между страницами или поведение выше
baseline context limit. Из этой оценки токенов не следует ускорение.
Ни выгодные проценты сырого вывода, ни эти небольшие синтетические задачи
не доказывают универсальное улучшение токенов, контекста, стоимости или качества
ответов.
