# Перенос существующей памяти на Richi

[English](MIGRATION.md) | Русский

Все обращения должны идти через установленную команду `richi`: терминал,
агенты и ярлык карты используют один пакет и одну конфигурацию. Обёртки прежних
Python-скриптов больше не устанавливаются. Перенос сохраняет накопленные знания,
историю, Git-снимки и остальные локальные материалы.

<a id="preparation"></a>
## Подготовка

1. Установите Richi обычным `pip install .` в отдельное Python-окружение по
   [инструкции](INSTALLATION.ru.md). Если раньше использовалась editable-установка,
   переустановите пакет через `pip install --force-reinstall /path/to/Richi`.
   Для работы над функциями задайте `development.source` и включите `dev`
   командами `richi config set`; установка остаётся фиксированной.
2. Запишите фактический путь к существующей базе. Команды переноса выполняйте в
   обычном терминале без `RICHI_DB`, `RICHI_CONFIG` и `RICHI_DATA_DIR`.
   Явный `-w default` позволяет указать путь к файлу, даже если для терминала
   по умолчанию выбран именованный workspace.

   ```sh
   richi -w default --db /path/to/old-data/memory.sqlite3 check
   richi -w default --db /path/to/old-data/memory.sqlite3 project list
   richi -w default --db /path/to/old-data/memory.sqlite3 recall 'известное решение'
   ```

3. Сохраните прежний конфиг, инструкции агента и ярлык для диагностики. Запишите
   список проектов и несколько известных записей для проверки после переноса.
4. Приостановите задачи, записывающие в старую базу, и завершите серверы карты,
   использующие её. Не позволяйте старому и новому расположениям стать двумя
   независимо пополняемыми копиями памяти.

<a id="moving-data"></a>
## Перенос данных

Перед копированием выберите место назначения.

- Для `default` выберите постоянный каталог вне репозитория с исходниками,
  окружения Python и каталогов других workspace. При необходимости создайте его.
- Для нового именованного workspace выполните `richi workspace create NAME`.
  Команда `richi -w NAME workspace current` покажет путь назначения в поле
  `database`. Файл по этому пути должен отсутствовать (`initialized: false`).
  Его создаст команда резервного копирования, поэтому пропустите `init`.

В примере ниже подставьте путь к исходной базе и выбранный путь назначения.

```sh
richi -w default --db /path/to/old-data/memory.sqlite3 backup \
  --output /path/to/richi-data/memory.sqlite3
richi -w default --db /path/to/richi-data/memory.sqlite3 check
```

`backup` использует SQLite backup API и не перезаписывает существующий файл.
Копирование только активного `.sqlite3` файловым менеджером не гарантирует
целостность при WAL. Исходную базу сохраните как резервную копию до завершения
проверок; не переносите к новой базе старые файлы `-wal` и `-shm`.

Сохраните структуру каталогов сопутствующих данных:

- `artifacts/git/` со всеми захваченными байтами кода;
- существующие `backups/`, архивы и локальные отчёты;
- частные evaluation-наборы, их исходные снимки, ожидания и результаты;
- документы, manifest-файлы и прочие материалы, на которые ссылаются источники.

SQLite backup не включает эти файлы. Сверьте список и хеши скопированных файлов;
после переноса проверьте чтение нескольких захваченных Git-источников. Нужные
Git-объекты зарегистрированных репозиториев также должны оставаться доступны.
PID-файлы, сокеты и locks старого `runtime/` переносить не нужно: новый сервер
создаст своё состояние при запуске.

Абсолютные ссылки на прежние локальные документы могут требовать сохранения
архива по старому пути либо точечного исправления проверенных ссылок. Не меняйте
массово происхождение исторических свидетельств и не присваивайте им новый HEAD.
Manifest-файлы проверки источников привязаны к пути базы: сохраните старые как
историю, а для проверок нового расположения создайте новую baseline через
`sources snapshot`. Частные evaluation-снимки и ожидания не переписывайте ради
успешного результата; новую конфигурацию запуска храните отдельно.

<a id="switching-the-command-agent-and-map"></a>
## Переключение команды, агента и карты

1. Для `default` команда `richi -w default workspace current` покажет путь к
   зарегистрированному конфигу в поле `config_file`. В этом файле задайте новый
   абсолютный путь к базе в поле `database`. При необходимости создайте
   JSON-файл и его родительский каталог. В существующем файле сохраните
   остальные настройки. Конфиг именованного workspace уже указывает на его базу.
   Уберите прямые переопределения хранилища также из окружения агента.
2. Для Codex, Claude Code, Cursor и Antigravity установите или подключите существующий скилл
   по [инструкции по настройке](SETUP.ru.md). Для клиента с ручной настройкой
   сохраните локальные дополнения, скопируйте каталог `skills/richi` в папку
   скиллов клиента и переместите старую копию `project-memory` за пределы этой
   папки. Обновите инструкции проекта, в которых скилл вызывается по старому имени.
   В проектных инструкциях замените
   вызовы старых `memory.py`, `serve.py`, `launch_map.py` прямыми командами `richi`.
   Сохраните разрешения на запись и правила проверки источников.
3. В терминале выполните `richi -w NAME config show` и `richi -w NAME check`,
   подставив имя целевого workspace. В новом чате выберите этот workspace
   и проверьте ту же базу командами `richi config show` и `richi check`.
   В Cursor в каждом вызове сразу после `richi` подставляйте точный аргумент
   `--chat` из хука `sessionStart` текущего чата.
4. Для ярлыка карты используйте `richi -w NAME map` с именем этого workspace.
   Если у ярлыка другой PATH, укажите абсолютный путь к `richi`.
5. Повторите известные запросы, сравните проекты и записи, откройте карту,
   источники, историю и diff. Убедитесь, что новый сервер использует новую базу.
6. Уберите прежние исполняемые скрипты и обёртки из рабочих путей. Архив исходного
   инструмента можно сохранить как локальный исторический материал. Старые
   инструкции в уже открытых чатах обновите или явно укажите им использовать
   установленный `richi`; перенаправления старых вызовов больше нет.

Если переносится checkout зарегистрированного проекта, обновите полный объект
`project` через `project upsert`, сохранив остальные поля. Независимые клоны
автоматически не считаются одним репозиторием. Подробнее — в
[Git-справочнике](../skills/richi/references/GIT.ru.md).

<a id="database-schema-and-migration-recovery"></a>
## Схема базы и исправление ошибок переноса

Смена способа запуска и переключение `dev` не меняют схему SQLite, выбранную базу
и формат Git-источников. Чтобы вернуться к установленному коду, выполните
`richi config set dev false`; возврат старой копии базы для этого не нужен. Richi
продолжает читать существующие знания, включая ранее записанные `git:` ссылки.
Если `check` сообщает о неизвестной схеме, сохраните базу и проверьте указанную
версию. Для обновления схемы 1 или 2 до схемы 3 выполните
`richi migrate` в нужном workspace. Команда сначала создаёт резервную копию. Подробнее в
[справочнике графа](../skills/richi/references/GRAPH.ru.md).

До возобновления записи можно вернуться к исходному workspace или восстановить
прежнее значение `database` в конфиге `default`. После появления новых записей в новом хранилище
возвращать старую копию поверх него нельзя: это потеряет работу других агентов.
Сначала остановите запись и сохраните обе базы, затем разберите расхождения
через штатные команды и историю. Для точечных исправлений записей используйте
`expected_updated_at`. Старый архив не должен снова стать рабочим хранилищем
из-за забытого ярлыка или инструкции.
