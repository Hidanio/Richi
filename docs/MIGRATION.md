# Перенос существующей памяти на Richi

Все обращения должны идти через установленную команду `richi`: терминал,
агенты и ярлык карты используют один пакет и одну конфигурацию. Обёртки прежних
Python-скриптов больше не устанавливаются. Перенос сохраняет накопленные знания,
историю, Git-снимки и остальные локальные материалы.

## Подготовка

1. Установите Richi по [инструкции](INSTALLATION.md). Для работы над новыми
   функциями используйте отдельное Python-окружение и `pip install -e`.
2. Проверьте существующую базу по её фактическому пути:

   ```sh
   richi --db /path/to/old-data/memory.sqlite3 check
   richi --db /path/to/old-data/memory.sqlite3 project list
   richi --db /path/to/old-data/memory.sqlite3 recall 'известное решение'
   ```

3. Сохраните прежний конфиг, инструкции агента и ярлык для диагностики. Запишите
   список проектов и несколько известных записей для проверки после переноса.
4. Приостановите задачи, записывающие в старую базу, и завершите серверы карты,
   использующие её. Не позволяйте старому и новому расположениям стать двумя
   независимо пополняемыми копиями памяти.

## Перенос данных

Выберите постоянный каталог Richi вне checkout и окружения Python. Платформенные
каталоги по умолчанию перечислены в [настройках](INSTALLATION.md#выбор-хранилища).
Следующие пути синтетические: замените их своими, а каталог назначения создайте
до выполнения команды.

```sh
richi --db /path/to/old-data/memory.sqlite3 backup \
  --output /path/to/richi-data/memory.sqlite3
richi --db /path/to/richi-data/memory.sqlite3 check
```

`backup` использует SQLite backup API и не перезаписывает существующий файл.
Копирование только активного `.sqlite3` файловым менеджером не гарантирует
целостность при WAL. Исходную базу сохраните как резервную копию до завершения
проверок; не переносите к новой базе старые файлы `-wal` и `-shm`.

Сохраните структуру каталогов сопутствующих данных:

- `artifacts/git/` со всеми захваченными байтами кода;
- существующие `backups/`, архивы и локальные отчёты;
- частные evaluation-наборы, их исходные снимки, ожидания и результаты;
- документы, manifest-файлы и прочие материалы, на которые ссылаются источники.

SQLite backup не включает эти файлы. Сверьте список и хеши скопированных файлов;
после переноса проверьте чтение нескольких захваченных Git-источников. Нужные
Git-объекты зарегистрированных репозиториев также должны оставаться доступны.
PID-файлы, сокеты и locks старого `runtime/` переносить не нужно: новый сервер
создаст своё состояние при запуске.

Абсолютные ссылки на прежние локальные документы могут требовать сохранения
архива по старому пути либо точечного исправления проверенных ссылок. Не меняйте
массово происхождение исторических свидетельств и не присваивайте им новый HEAD.
Manifest-файлы проверки источников привязаны к пути базы: сохраните старые как
историю, а для проверок нового расположения создайте новую baseline через
`sources snapshot`. Частные evaluation-снимки и ожидания не переписывайте ради
успешного результата; новую конфигурацию запуска храните отдельно.

## Переключение команды, агента и карты

1. Запишите новый путь `database` в конфигурацию Richi. При необходимости задайте
   `data_dir`; обновите или уберите переопределения `RICHI_DB` и `RICHI_CONFIG`
   в оболочке, IDE и среде агента. Конфигурация сама не перемещает данные.
2. Проверьте `richi config show` и `richi check` из терминала и из среды агента.
   Они должны выбирать одну и ту же перенесённую базу.
3. Установите целиком актуальную папку `skills/project-memory`, предварительно
   сохранив локальные дополнения прежнего skill. В проектных инструкциях замените
   вызовы старых `memory.py`, `serve.py`, `launch_map.py` прямыми командами `richi`.
   Сохраните разрешения на запись и правила проверки источников.
4. Переведите ярлык карты на `richi map`; для разработки используйте
   `richi map --dev`. GUI-ярлыку может потребоваться абсолютный путь к команде,
   если он не наследует PATH терминала.
5. Повторите известные запросы, сравните проекты и записи, откройте карту,
   источники, историю и diff. Убедитесь, что новый сервер использует новую базу.
6. Уберите прежние исполняемые скрипты и обёртки из рабочих путей. Архив исходного
   инструмента можно сохранить как локальный исторический материал. Старые
   инструкции в уже открытых чатах обновите или явно укажите им использовать
   установленный `richi`; перенаправления старых вызовов больше нет.

Если переносится checkout зарегистрированного проекта, обновите полный объект
`project` через `project upsert`, сохранив остальные поля. Независимые клоны
автоматически не считаются одним репозиторием. Подробнее — в
[Git-справочнике](../skills/project-memory/references/GIT.md).

## Схема базы и исправление ошибок переноса

Смена способа запуска не меняет схему SQLite и формат Git-источников. Richi
продолжает читать существующие знания, включая ранее записанные `git:` ссылки.
Это поддержка формата данных, а не старых исполняемых скриптов. Если `check`
сообщает неизвестную схему, разберите причину; не удаляйте базу ради переустановки.
Для схемы 1 переход к графу выполняется отдельно через backup и явный `migrate`,
как описано в [справочнике графа](../skills/project-memory/references/GRAPH.md).

До возобновления записей ошибочное переключение можно исправить выбором прежней
целой базы в конфигурации. После появления новых записей в новом хранилище
возвращать старую копию поверх него нельзя: это потеряет работу других агентов.
Сначала остановите запись и сохраните обе базы, затем разберите расхождения
через штатные команды и историю. Для точечных исправлений записей используйте
`expected_updated_at`. Старый архив не должен снова стать рабочим хранилищем
из-за забытого ярлыка или инструкции.
