# Переключение существующей памяти на Richi

Переносится реализация инструмента. База знаний, её история, Git-снимки и
зарегистрированные репозитории могут остаться на прежнем месте. Не нужно
экспортировать их в Git или создавать новую пустую базу вместо старой.

## Подключение без переноса данных

1. Установите Richi в виртуальное окружение по [инструкции](INSTALLATION.md).
2. Проверьте существующее хранилище, явно указав его фактический путь:

   ```sh
   richi --db /path/to/existing/memory.sqlite3 check
   richi --db /path/to/existing/memory.sqlite3 project list
   richi --db /path/to/existing/memory.sqlite3 backup
   ```

3. Запишите путь `database` в локальный JSON-конфиг вне репозитория и подключите
   его через `RICHI_CONFIG` или `--config`. Либо используйте переменную `RICHI_DB`.
   Проверьте выбранный путь через `richi config show`, затем выполните несколько
   известных запросов `recall` и откройте карту.
4. Настройте для агента ту же команду и конфигурацию. Сохраните резервную копию
   прежнего skill; установите целиком переносимую папку `skills/project-memory`.
   Локальные дополнения и разрешение на запись перенесите в инструкции проекта
   или локальные настройки агента.

Схема SQLite и формат Git-источников при таком переключении не меняются.
Новая упаковка сама не запускает `migrate`. Если `check` сообщает неизвестную
или неподдерживаемую схему, разберите причину; не удаляйте базу ради переустановки.
Для старой схемы 1 переход к графу выполняется отдельно через backup и явный
`migrate`, как описано в [справочнике графа](../skills/project-memory/references/GRAPH.md).

## Совместимость старых вызовов

Старые чаты и ярлыки могут продолжать вызывать `memory.py`, `serve.py` или
`launch_map.py` из прежней папки. Для них предусмотрен локальный переходный
адаптер. Он заменяет только эти три точки входа небольшими обёртками и сохраняет
оригиналы с хешами и manifest для возврата. Остальные старые модули и данные
остаются на месте.

Из корня checkout Richi:

```sh
python scripts/install_legacy_bridge.py \
  --legacy-dir /path/to/legacy-memory \
  --python /path/to/Richi/.venv/bin/python
```

Папка `--legacy-dir` должна содержать существующую `memory.sqlite3` и все три
обычных файла точек входа. Проверка базы новой установленной версией выполняется
до замены. Переданный Python должен принадлежать окружению с установленным Richi.
После успешной установки сохраните путь `manifest` из JSON-ответа.

Обёртки передают прежнюю базу явно; старый вызов не переключается на новую пустую
базу по умолчанию. Они используют установленный пакет и выбранное виртуальное
окружение, поэтому эти пути должны оставаться доступными. Повторная установка
поверх уже работающего адаптера отклоняется: сначала восстановите оригиналы.
Импорты прежних модулей также перенаправляются к установленному пакету; это
сохраняет Git-worker уже открытой карты. Для таких импортов нужен Python 3.9+
и доступный каталог установленного пакета. Установка адаптера не изменяет
старые инструкции чатов автоматически.

Проверьте старый вызов `python3 /path/to/legacy-memory/memory.py check` и новый
`richi check`: оба должны использовать ожидаемую базу. Проверьте известный запрос
и повторный запуск карты. Уже запущенный сервер сохраняет свой обработчик HTTP,
а новые дочерние вызовы старых точек входа используют установленный Richi. Новый
запуск выбирает сервер с поддержкой standalone runtime. Перезапуск
запускателя сам по себе не означает, что старый процесс остановлен.

## Возврат

```sh
python scripts/install_legacy_bridge.py \
  --restore /path/to/legacy-memory/richi-bridge-backup-EXAMPLE/manifest.json
```

Используйте точный путь из результата установки. Скрипт сверяет все три текущие
обёртки и резервные копии перед восстановлением. Если кто-то изменил эти файлы,
возврат остановится, чтобы не затереть новые правки; разберите расхождение.
База при возврате адаптера не откатывается, поэтому новые знания сохраняются.
Для возврата skill восстановите его отдельно сохранённую копию и прежнюю локальную
настройку команды, если вы их меняли.

Не восстанавливайте старый SQLite backup поверх работающей базы: это может
удалить более поздние записи других агентов. Для исправления конкретного знания
используйте историю и штатные команды с `expected_updated_at`. Проверка
read-only копии через `--db` подходит для сравнения и диагностики.

## Если позже потребуется перенести сами данные

Отдельно запланируйте остановку записывающих процессов и используйте SQLite
backup API. Одной копии активного файла `.sqlite3` недостаточно при WAL.
Кроме базы сохраняйте `artifacts/git/` и нужные Git-объекты исходных репозиториев;
SQLite backup не включает исторические байты кода автоматически.

Изменение пути базы требует повторной проверки manifest-файлов наблюдения
источников: они привязаны к исходному пути и не являются переносимым backup.
При переносе checkout проекта обновите полный объект `project` через
`project upsert`; отдельные клоны не считаются одним репозиторием автоматически.
Существующие абсолютные ссылки на исторические локальные документы остаются
свидетельствами своего места и времени; не переписывайте их массово как
проверенные ссылки на новый HEAD. Правила переноса описаны в
[Git-справочнике](../skills/project-memory/references/GIT.md).
