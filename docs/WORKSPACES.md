# Рабочие области

Workspace объединяет несколько связанных проектов и их знания. У каждой области
своя SQLite-база, история записей, определения, связи, Git-снимки, настройки и
логи карты. Один репозиторий можно добавить в несколько workspace: проекты и
знания регистрируются независимо в каждой базе, совпадающие ID не пересекаются.
Поиск и граф работают только с выбранной областью.

## Создание и переключение

```sh
richi workspace list
richi workspace current
richi workspace create work
richi -w work init
richi -w work project add /path/to/service-api
richi -w work project add /path/to/service-storage --id storage
richi use work
richi project list
richi map
```

`workspace create` создаёт настройки пустой области; `init` явно создаёт её базу.
Команды не копируют знания из текущей области и не клонируют репозитории.
`project add` принимает существующую папку и сохраняет её абсолютный путь.
По умолчанию ID и имя проекта берутся из имени папки; доступны `--id`, `--name`
и `--description`. Повторное добавление того же ID и пути сохраняет ранее
записанные метаданные. При конфликте ID с другим путём команда выдаёт ошибку.
Для осознанного редактирования метаданных остаётся `project upsert --json FILE`.

```sh
richi use personal
richi use default
# В терминале без имени — пронумерованный список для быстрого выбора:
richi use
```

Переключение меняет область по умолчанию для последующих команд. Оно не
останавливает уже запущенные операции и карты. В неинтерактивной среде имя
обязательно: Richi не пытается читать меню из входного JSON агента.

`default` использует существующую конфигурацию и память: установка поддержки
workspace не переносит и не разделяет старые записи. Для новых областей Richi
выделяет отдельные каталоги `workspaces/NAME/` внутри платформенного каталога
данных. Реестр `workspaces.json` хранится в платформенном каталоге конфигурации.
Фактические пути показывает `richi -w NAME config show`.

В обычном терминале явный `--config` или `-w` выбирает конфигурацию;
затем учитываются `RICHI_CONFIG`, `RICHI_WORKSPACE` и сохранённый CLI default.
Прямой config не используется одновременно с явным workspace. Правила ниже
закрепляют отдельный выбор для обнаруженного чата.

## Выбор области для чата

Текущий workspace CLI и workspace чата — разные настройки. `richi use work`
меняет выбор для обычных вызовов из терминала. Новый чат сначала спрашивает:
использовать текущий CLI workspace или выбрать другой только для этого чата.

```sh
richi chat current
richi workspace list
# После ответа пользователя — один из вариантов:
richi chat bind --current
richi chat bind work
```

Выбор сохраняется для конкретного ID чата и не меняет глобальный CLI default.
`--current` фиксирует текущее значение: последующий `richi use personal` в
терминале не перенаправит уже связанный чат. Повторять вопрос на каждом сообщении
или после восстановления контекста не нужно. Если пользователь уже явно назвал
workspace в этом чате, агент использует этот выбор без повторного вопроса.

В Codex launcher получает ID из `CODEX_THREAD_ID`. Для других интеграций:

```sh
richi --chat task-123 chat bind work
richi --chat task-123 project list
# Только по явному указанию изменить область этого чата:
richi --chat task-123 chat bind personal --replace
```

Можно задать `RICHI_CHAT_ID` вместо флага; явный `--chat` имеет приоритет.
Без выбора обнаруженный чат не читает и не записывает знания даже с `-w`.
Повторяющий выбранную область `-w` допустим, другая область и прямые
переопределения базы/config отклоняются. `chat current`, список областей и
справка доступны до выбора; повреждённый dev не мешает управлению привязкой.
Это защита от случайного смешения контекста, а не авторизация пользователей ОС.
CLI не умеет сам показать вопрос внутри чужого чата: вопрос задаёт агент по
skill/AGENTS, а launcher проверяет наличие и согласованность выбора.

## Состояние workspace и путей проектов

```sh
richi status
richi --project-path /path/to/checkout status --project service-api
richi status --projects --limit 50
```

`status` выдаёт единый JSON: выбор чата и CLI, фактический workspace, пути
конфигурации и базы, установленный/dev runtime, состояние базы и принадлежность
указанного пути. По умолчанию проверяется текущая рабочая папка; `--project`
проверяет ожидаемый ID, но не выбирает область. Для workspace-wide работы
незарегистрированная текущая папка допустима, однако её знания нельзя считать
проверенными для конкретного проекта.

`--projects` добавляет диагностику всех зарегистрированных путей: отсутствующие
папки, недоступные каталоги, повреждённые Git-регистрации, дубли и worktree.
Проект без локального пути отмечается информационно. Обычный вызов тоже может
проверять пути из реестра для сопоставления текущего проекта, но не выдаёт полный
аудит. Проверка использует правила `project check` и только выбранную базу.

`--limit` (1–200, по умолчанию 50) ограничивает детали в ответе; проблемные пути
показываются первыми. `total`, `checked`, `omitted`, `counts` и `status` описывают
покрытие: пропущенные детали или неполная проверка не означают отсутствие проблем.
Внутренний бюджет — 10 секунд и 10000 регистраций; launcher ограничивает worker
30 секундами. Не завершившаяся проверка не подтверждает принадлежность проекта.

До привязки чата возвращается `selection_required` с вариантами следующих
команд, без чтения настроек runtime, базы или путей проектов. При сломанном dev
сохраняются доступные метаданные и ошибка; установленная версия не подставляется
вместо выбранной. Привязка и выбор конфигурации фиксируются для одного вызова.

Поле верхнего уровня `status`: `ok`, `attention`, `selection_required` или
`unavailable`. Код выхода 0 означает, что отчёт сформирован, а не что всё исправно;
автоматизация должна проверять `status` и покрытие диагностики. Ошибочные аргументы,
конфликт workspace или повреждённая конфигурация дают JSON-ошибку и код 1.
Команда ничего не инициализирует, не переносит, не мигрирует и не исправляет.
Она читает метаданные базы и реестр проектов, а не записи знаний; для проверки
содержимого остаются `check` и явно запрашиваемый `punisher`.

## Добавление папки с репозиториями

```sh
richi -w work project scan /path/to/repositories
richi -w work project scan /path/to/repositories --apply
```

Первый вызов показывает найденные репозитории, объединённые worktree,
пропуски и конфликты; второй регистрирует результат одной транзакцией.
По умолчанию глубина обхода — 3, её можно задать через `--max-depth`.
Сканирование не заходит в исходники уже найденного checkout, скрытые каталоги,
vendor, node_modules и виртуальные окружения, не следует по вложенным symlink.
Корень сканирования тоже должен быть настоящим каталогом: для symlink укажите его целевой путь.
Оно не клонирует код, не импортирует прежние знания и не включает наблюдение за
папкой: новые checkout добавляются при следующем запуске.

Существующие ID, описания и пути сохраняются. Git worktree сопоставляются по
общему Git-каталогу; отдельные клоны не объединяются только по remote URL.
При конфликте ID, ошибке или неполном обходе `--apply` не добавляет часть списка.
Превью отражает текущее состояние; применение заново проверяет каталог и коллизии.
Один репозиторий можно независимо зарегистрировать в другой области.

## Проверка проекта перед операцией

```sh
richi -w work project check /path/to/checkout --id service-api
richi -w work --project-path /path/to/checkout recall 'кеш' --project service-api
richi -w work --project-path /path/to/checkout entry put --json result.json
```

`project check` показывает статус сопоставления, область, базу и проект.
Проверка использует только выбранную область: совпадение в другой базе не
подходит. Вложенный самостоятельный Git-репозиторий не относится автоматически
к внешнему проекту. Неоднозначные регистрации требуют исправления.

`--project-path` повторяет проверку в транзакции операции и отклоняет неизвестный
путь или несовпадающий `--project`. У записываемых entry проверенный проект должен
входить в `project_ids`; остальные связанные проекты в том же workspace разрешены.
Для workspace-wide знаний и администрирования путь можно осознанно не передавать.
Флаг не проверяет смысл текста и не заменяет проверку источников.
Создание базы, её миграция и backup, регистрация проектов и запуск карты
отклоняют этот флаг: это операции над workspace или его реестром.
Для карты выполните `project check` отдельно: карта отображает весь workspace.

## Код, режим разработки и карта

Изоляция касается памяти Richi. Если в двух workspace указан один путь
репозитория, файлы и рабочая копия Git общие: изменение кода видно обоим.
Для независимых изменений подключайте разные Git-worktree или checkout.
Richi не создаёт их автоматически и не предоставляет разграничение доступа
между пользователями операционной системы.

Новая область наследует текущие `dev` и `development.source` при создании.
Далее её настройки независимы:

```sh
richi -w work config set development.source /path/to/Richi
richi -w work config set dev true
richi -w personal config set dev false
```

Dev и обычная версия внутри одного workspace используют одну базу. Переключение
режима не переносит знания между областями и не применяет миграции SQLite.
Изменения установленного launcher требуют переустановки пакета.

`richi -w work map` открывает карту этой области. Карта показывает имя workspace
и остаётся привязана к своей базе, даже если позднее вызвать `richi use personal`.
Для другой области запускается отдельная карта на свободном локальном порту.
Настройка dev и перезагрузка исходников также остаются привязаны к исходной
области. Переключение default не меняет содержание уже открытой вкладки.
