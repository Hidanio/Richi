# Отбор кандидатов recall: проблема, гипотезы и проверка

Протокол зафиксирован до реализации, 16 октября 2026. Основа отдельного PR —
`e1265bb82674e0c7cb9f16763ab6f67919d9ad20`. На момент начала работы PR #7 ещё
не влит в main: его зафиксированные измерения используются как свидетельство,
но ветка PR #7 не становится зависимостью реализации.

## Наблюдаемая проблема

В [неизменяемом отчёте PR #7](https://github.com/Hidanio/Richi/blob/ff966896ec9c28497430ec18b2c39706ee86d5ab/evals/results/memory-growth-2026-10-15.json)
обычный recall по `task:DEMO-84` возвращал 6354 символа и задачу на первом месте,
но диагностический проход просматривал 105/1005/10005 entries при росте корпуса
до 106/1006/10006 записей. Медианы CLI составляли 280,6/321,1/696,2 мс.
Это три повтора на одной машине, а не доказанный закон роста или SLA.

В исходном `candidates` FTS shortlist дополняется полным чтением допустимых
по состоянию entries: для каждой декодируются поля и вычисляется lexical score,
хотя многие записи затем отбрасываются. Обход нужен в том числе для прежних
совпадений ID/Jira/aliases, которые токенизация FTS может пропустить.
Проверяемая проблема — объём ненужной загрузки и обработки полных карточек.

## Гипотезы до изменения

1. Предварительный отбор по FTS и метаданным, сохраняющий все прежние способы
   попадания в кандидаты, уменьшит число полных загрузок и вызовов lexical
   scoring. Выигрыш должен проявиться в счётчиках выполненной работы, а затем
   проверяться обычным CLI-замером без диагностической нагрузки.
2. Сохранение Unicode-семантики ID/aliases может потребовать линейного обхода
   метаданных. Нельзя без проверки заменить Python-нормализацию на SQL
   `lower`/сравнение строк. Этот этап не обещает устранить O(N), физические
   чтения SQLite или гарантировать использование индекса.
3. Оптимизация предварительного отбора может сохранить прежний результат:
   refs и их порядок, источники, состояния, проектный boost и графовое
   дополнение. Полная загрузка карточек остаётся нужна для реально выбранных
   кандидатов; FTS-off сохраняет существующий fallback.

Пропуск выбранной цели широкого `receipt calibration` — отдельная задача
качества обнаружения. В PR #7 он возникал во всех семи наборах, при этом
уникальный запрос находил ту же запись. Это не доказывает нерелевантность
остальных совпадений и не даёт основания менять ранжирование, лимиты,
состояния или oracle ради ускорения. Архив, схема хранения, удаление знаний
и пользовательская память в этот этап не входят.

## Контракт выбранной реализации

При FTS текущий отбор читает метаданные entries курсором, затем получает
полные записи по первичному ключу для FTS/ID/Jira/alias-кандидатов. Поэтому
`entries_scanned` продолжает считать все посещённые entries разрешённых
состояний, а `entries_scored` — только полный lexical scoring прямого поиска.
Обход метаданных остаётся O(N); оптимизируется обработка полных карточек.
`entries_prefiltered` считает исключённые записи; сумма scored и prefiltered
равна scanned. Это разделение работы, а не обещание постоянного числа SQL-строк
или физических чтений. Entities и полный fallback без FTS сохраняются.
Для прямого API-вызова публичный `recall` открывает read-транзакцию, если её
ещё нет, и сохраняет транзакцию вызывающего; CLI уже выполнял чтение в транзакции.
Это удерживает единый снимок при параллельной записи, в том числе после
предвыборки последней строки курсора Python, когда одного курсора недостаточно.

Без полного чтения причина исключения — `routing_prefilter`. Только для
исключённой entry из `--expect` допускается одна отдельная полная проверка:
`expected_entry_probes <= 1`. Она уточняет прежний lexical guard относительно
выполненного shortlist, но не добавляет кандидата и не входит в scored;
запись остаётся учтённой в prefiltered. Полный контракт счётчиков — в
[DIAGNOSTICS.md](../skills/project-memory/references/DIAGNOSTICS.md).
Дополнительные поля диагностики занимают бюджет и могут изменить её сокращение;
цель сохранения обычной выдачи проверяется отдельно от диагностического JSON.

## Протокол сравнения и приёмка

1. Сохранить исходные ожидания. Использовать без изменений
   [fixture](https://github.com/Hidanio/Richi/blob/ff966896ec9c28497430ec18b2c39706ee86d5ab/evals/memory_growth_cases.json)
   и [runner PR #7](https://github.com/Hidanio/Richi/blob/ff966896ec9c28497430ec18b2c39706ee86d5ab/evals/evaluate_memory_growth.py).
   Исходный raw JSON не переписывать; результаты повторного baseline и новой
   реализации сохранять отдельно. Скрипты измерений можно читать из отдельного
   checkout PR #7, не включая его изменения в самостоятельный PR реализации.
2. Установить baseline и candidate обычными пакетами в разные disposable venv.
   Сравнивать одинаковые синтетические корпуса, запросы, флаги, `limit=8`
   и normal budget 16000. Сохранить hashes fixture/runtime, версии Python/SQLite,
   backend, параметры и сырые повторы. Живую память и пользовательские
   runtime/config/chat bindings не использовать и не переключать.
3. До реализации зафиксировать дополнительные контрастные и отрицательные
   случаи: соседний Jira/ID, пустой результат, Unicode и неоднозначные aliases,
   confirmed/hypothesis/superseded с явными флагами, FTS-off, графовое дополнение
   и его ограничения, entries и entities/concepts. Fixture PR #7 не содержит
   entities, поэтому он один не подтверждает сохранение этой ветки поиска.
4. Сравнить обычную выдачу baseline/candidate: упорядоченные refs и позиции,
   источники, knowledge/work states, применимость, графовые связи и no-match.
   Сохранить бюджет и признаки пропусков. Точный get и полные текущие записи
   остаются доступны. Различия не объяснять ускорением: каждое требует разбора.
   Прежние misses честно остаются в отчёте; их наличие не является успехом
   качества, а исчезновение не должно маскировать непреднамеренную смену семантики.
5. Диагностику `--expect` с бюджетом 100000 выполнять отдельно. Различать
   просмотр метаданных, полную загрузку и lexical scoring; счётчики должны
   описывать реально выполненную работу. Если названия или смысл счётчиков
   меняются, явно сопоставить старую и новую методику. Уменьшение полных загрузок
   не называть уменьшением числа физических чтений без отдельного измерения.
6. Проверить неизменность данных, истории, графа и состояний; пройти
   `python -m unittest discover -s tests -v` и `python evals/evaluate_recall.py`.
   CLI-время измерять отдельно от seed, JSON parsing и проверок; первый вызов
   отдельно от повторов. Кеши не считаются холодными, p95 из трёх повторов
   равен максимуму. Абсолютный порог времени не становится CI gate.

Приёмка требует сохранения поведения и подтверждённого уменьшения ненужной
обработки полных записей на выбранных сценариях. Выигрыш времени публикуется
только по фактическим замерам, включая отсутствие улучшения и оставшиеся
линейные проходы. Изменение metadata scan, latency и качества поиска — разные
результаты; ни один из них не заменяет остальные.

## Результаты и воспроизведение

Повторный [baseline](../evals/results/recall-candidates-before-2026-10-16.json)
и [candidate](../evals/results/recall-candidates-after-2026-10-16.json) измерены
16 октября 2026 по Москве последовательно на macOS arm64, Python 3.9.6,
SQLite 3.43.2. Ниже медианы трёх повторов обычного `current-id`; первый вызов
учтён отдельно. Число полных lexical scoring до изменения равно прежнему
`entries_scanned`, после — новому `entries_scored`.

| Background entries | Полный scoring до → после | `entries_scanned` после | Медиана до → после, мс | Изменение |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 105 → 3 | 105 | 293,434500 → 286,808500 | −2,3% |
| 1000 | 1005 → 3 | 1005 | 335,029292 → 295,540000 | −11,8% |
| 10000 | 10005 → 3 | 10005 | 598,241916 → 313,238500 | −47,6% |

В этих трёх случаях `expected_entry_probes=0`; metadata scan остаётся линейным.
Во всех 77 парах совпали записанные normal-поля, кроме времени, включая refs,
позиции и бюджеты; совпали корпуса и полные чтения с источниками и состояниями.
Оба прогона завершились без ошибок harness и нарушений инвариантов, данные
остались неизменными. Семь пропусков цели широкого запроса сохранились:
`quality_expectations_met=false`. Это проверка сохранения поведения, а не
исправление качества широкого поиска.

Равномерного ускорения нет: например, `b100-d0-h0/crowded-lexical` вырос с
291,4 до 372,6 мс (+27,9%), `b1000-d0-h0/shared-jira` — с 316,0 до 359,2 мс
(+13,7%). Все 11 запросов `b10000-d0-h0` снизили медиану на 24,7–57,2%, но
три повтора на неконтролируемом хосте не отделяют шум от эффекта и не задают SLA.
При большом числе совпадений точного Jira/alias или shortlist выгода падает;
если совпадают все N записей, возможны N полных загрузок отдельными PK lookup.
Ускорение для любых распределений aliases не обещается; рост entities здесь
не измерен, а fallback без FTS сохраняет полный проход.

Проверки реализации: 14 новых тестов; итог suite — 564 passed и 1 skipped
из 565. Первоначальные 29 `PermissionError` на `socket.bind` в sandbox
перепроверены отдельно с разрешённым localhost: все 29 прошли. Acceptance —
7/7, база не изменилась.

Для обоих замеров использованы неизменённые runner/fixture из `ff96689`.
Пакет baseline установлен из того же commit: его production runtime совпадает
с `e1265bb`. Из семи сохранённых хешей runtime изменился только `recall.py`;
полные hashes, пути установленных venv, параметры и сырые повторы есть в JSON.
Исходный отчёт PR #7 сохранён. Для повторения из checkout candidate, когда
commit `ff96689` доступен локально, можно извлечь его во временную папку;
слияние PR #7 в main для этого не требуется. Каждый запуск пишет новый файл.

