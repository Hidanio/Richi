# Richi audit — 28 October 2026

English | [Русский](AUDIT-2026-10-28.ru.md)

The first phase reviewed a checkout based on `1baba5a` (`main`), using Python 3.9
on macOS. Scope: `src/richi/`, launcher/bootstrap, SQL schemas, the map, tests,
packaging and development instructions. Other branches and open PRs were outside
that phase. Checks use disposable databases and synthetic repositories, never
personal knowledge as test data.

The audit produced working-copy fixes. It does not prove the absence of all bugs
or imply a release publication or installation.

The installation/update continuation advanced local `main` to `6729d4c`, preserving
all fixes and integrating the merged installer. Current findings, GitHub status
and combined-build checks are in
[INSTALL_UPDATE_AUDIT-2026-10-28.md](INSTALL_UPDATE_AUDIT-2026-10-28.md).
The 599-test results below belong to the first phase, not the newer base.

## Clearer module boundaries

- CLI declarations moved from `memory.py` into `cli_parser.py`. The compatible
  `memory.parser()` entry remains. Argument parsing does not import heavyweight
  Git, search or map implementations; the parser receives required types/validators.
- Path-to-project membership rules moved into `projects.match_project`. `status`
  no longer calls another class's method with an unrelated object as `self`.
  Status and discovery keep their own budgets/caches and share selection rules.
- `sources related` reuses the Git path validator instead of duplicating similar
  checks.
- Git and graph HTTP workers share bounded reading while retaining distinct
  limits, protocols and error handling.

SQLite schema and record formats are unchanged. History, optimistic concurrency,
explicit migrations and workspace isolation remain. Idempotent `unchanged` with
an old `expected_updated_at` is an existing documented contract, not a new bug.

Independent core review found no new confirmed data-corruption risk. CLI batches
use `BEGIN IMMEDIATE`; writes, membership, history/events and FTS triggers share
a transaction. CAS is checked inside it and replay is tied to the payload hash.
Migration executes SQL without implicit commit, checks foreign keys/integrity
and changes `user_version` last. These are verified mechanisms and tested
scenarios, not guarantees for arbitrary damaged databases or direct third-party
SQLite writes.

## Remaining issues and next steps

### P2: Unicode normalization differs from FTS

Reproducer: confirmed entry `tree`, title `берёза контекст`, summary
`Recorded evidence.`, empty aliases and source `fixture://tree`. Neither
`recall береза` nor `recall берёза` returns the entry.
`--expect entry:tree --explain` reports `fts_not_shortlisted`.
This was reconfirmed after integrating `6729d4c` on a new synthetic schema 2 / FTS5
database. The newer index does not resolve the mismatch; exact `entry:tree`
retrieval returns the record.

`recall.normalize()` folds `ё` to `е`, while FTS indexes the original text.
The candidate is lost before Python scoring. This affects search completeness;
a missing result does not establish that the knowledge is absent. Exact-ID
reading works.

Next: align index/query normalization, define an explicit rebuild/migration for
existing indexes, and check FTS/scan parity on Unicode. Query variant enumeration
alone is not a sufficient fix: combinations grow and candidate caps introduce
additional bias. Normal CLI startup must not silently rebuild personal databases.

### P3: three atomic JSON writers and a config/workspaces cycle

`config`, `workspaces` and `installation` repeat temp-file/replace/fsync logic;
`chats` imports its writer from the domain module `workspaces`. The writers differ
in mode preservation, directory fsync and recovery after an error following
`replace`. `config` and `workspaces` have reverse lazy imports.

Next: extract independent path/JSON primitives with explicit policies and a
post-replace error contract. Blindly replacing every call with one helper risks
breaking distinct transaction obligations for workspace creation cleanup and
installed-version activation.

### P3: several response-budget algorithms

`compact`, `task_brief`, `git_impact` and diagnostics bound output differently,
with distinct payloads and required evidence. Next: share serialized-size
measurement and an explicit “card plus justification” preservation contract,
while retaining specialized selection policies. Do not replace them with generic
JSON truncation.

### P3: object sizes inside the graph worker

The new output limit protects HTTP-server buffers. The child process still
materializes full cards first: node/edge counts are bounded, aggregate content
size is not. Next: a separate export budget or streaming serialization with
explicit incompleteness. This is a residual resource risk, not a claim that a
crash was reproduced on personal data.

### Boundaries to preserve

- Bootstrap selects a working version before importing the launcher. Sharing a
  parser with a potentially damaged current runtime would break emergency rollback.
- Launcher owns workspace/chat/config and runtime selection; runtime owns knowledge
  and application commands. Dev mode does not replace the launcher.
- Projects, entry memberships and legacy relations already project into the graph
  through a registry/view. These preserve compatibility and relationship integrity;
  they do not justify a second mutable copy of the same data.
- Automatic ingestion, semantic search and extra domain-model layers are not
  required to fix the identified issues.

## First-phase verification

The checkout was normally installed with `pip install .` into a disposable venv.
Before testing, all 37 runtime/launcher/bootstrap files were compared byte for
byte with the installed copy; none differed.

- `python -m unittest discover -s tests -v`: 599 tests in 564.719 seconds;
  598 passed, one platform skip, no errors or failures.
- `python evals/evaluate_recall.py`: 7/7 cases; the synthetic database was unchanged.
- Independent review covered final fixes, parser extraction and shared worker
  handling. An AST comparison also confirmed CLI declaration preservation.
- `git diff --check`: passed.

The first-phase final run used macOS/Python 3.9; Linux and Python 3.12 were not run
locally. The public recall evaluation covers a limited synthetic set, not all
Unicode or graph sizes. Its 7/7 result does not invalidate the `е/ё` issue above.

The bootstrap fix reaches a permanent installation after launcher reinstallation.
Runtime changes are picked up on the next dev-mode invocation. The audit itself
did not replace the personal installation or publish releases.
