# Публичные синтетические оценки

[English](README.md) | Русский

<a id="recall-acceptance-cases"></a>
## Приёмочные случаи recall

Запускайте из репозитория интерпретатором Python из временного виртуального
окружения, в которое текущий checkout установлен обычным способом.
Одного `PYTHONPATH=src` недостаточно для launcher и метаданных пакета:

```sh
python evals/evaluate_recall.py
python evals/evaluate_recall.py --output /tmp/richi-recall-report.json
```

Каждый запуск создаёт и удаляет собственную временную SQLite-базу. Каждый вызов
CLI явно передаёт `--db` и пустой временный `--config`, очистив настройки
окружения `RICHI_*`. Пользовательская память, настроенные репозитории, внешние
сервисы и частные оценочные снимки не используются. Ссылки `example.test` —
вымышленные свидетельства; обращения к ним не выполняются.

Фиксированные синтетические случаи проверяют точные ID задач, Unicode aliases,
явные межпроектные связи, исключение исторических записей, неоднозначность и
область понятий, неизвестные запросы и различие реализации и релиза. Runner также
проверяет происхождение источников, knowledge/work states, бюджеты сериализованного
вывода и неизменность заполненной базы после recall. При провале случая он
завершается с ненулевым кодом и отказывается перезаписывать отчёты.

`recall_cases.json` содержит все исходные записи и ожидания. Это приёмочные
проверки, а не слепой benchmark и не заявление о точности recall в production.
Исторические частные наборы остаются вне репозитория; фикстура не заменяет их
и не воспроизводит их результаты.

<a id="memory-growth-measurements"></a>
## Измерения роста памяти

`evaluate_memory_growth.py` измеряет влияние роста синтетического корпуса
обычными чтениями Richi CLI. Фикстура `memory_growth_cases.json` фиксирует
параметры корпуса, запросы и ожидаемые полезные записи до измерения. Она
запускается отдельно от `evaluate_recall.py`; измерение роста не заменяет
существующие приёмочные случаи.

Используйте Python одноразового виртуального окружения, в которое текущий
checkout установлен обычным способом. Подпроцессы используют `-I` и очищают
унаследованные настройки Python, поэтому `PYTHONPATH=src` недостаточно.

```sh
python evals/evaluate_memory_growth.py --quick --repeats 1
python evals/evaluate_memory_growth.py --repeats 3 --output /tmp/richi-memory-growth-report.json
```

Для каждого отчёта используйте новый `--output`: существующий файл никогда
не перезаписывается. `--repeats` принимает 1–20, по умолчанию 3: каждый обычный
запрос имеет отдельно отражённый первый вызов и N измеряемых повторов.
`--timeout` принимает положительное конечное значение до 600 секунд, по
умолчанию 60. `--cases PATH` выбирает фикстуру. Полный запуск сравнивает
независимые оси:

| Ось | Значения полного запуска | Вопрос |
|---|---|---|
| Фоновые текущие entries | 100, 1000, 10000 | Как дополнительные текущие знания влияют на поиск и покрытие диагностики? |
| Дополнительные children с тем же Jira key | 0, 10, 100 | Вытесняют ли конкурирующие подробности задачу или полезные свидетельства при фиксированном лимите результатов? |
| Дополнительные ревизии истории задачи | 0, 10, 100 | Как растёт аудитная история при неизменном итоговом текущем содержимом? |

Это отдельные эксперименты, не декартово произведение. Общий baseline полного
запуска: background 100 / children 0 / revisions 0; всего семь разных наборов.
`--quick` использует baseline 8 / 0 / 0 и значения background 8/24,
children 0/3/12, revisions 0/2/5: шесть небольших наборов для smoke-проверки,
не измерение полной матрицы. Внутри каждой оси остальные измерения фиксированы;
сравниваются одинаковые запросы, лимиты, бюджеты и ожидания. В поставляемой
фикстуре всего текущих entries — шесть опорных записей плюс фон и дополнительные
children: крупнейший фоновый набор содержит 10006, а не 10000 entries.
Фикстура содержит `entity: []`; рост entities не измеряется. Число текущих записей
и аудитных ревизий отвечает на разные вопросы; по одному размеру SQLite-файла
нельзя установить причину изменения поиска или физический объём одной таблицы.

Обычные вывод и задержку CLI при `--max-chars 16000` измеряйте отдельно от
диагностического прохода `recall --expect` с `--max-chars 100000`. Обычный проход
определяет возвращённые refs, позиции целей, пропуски и сериализованный размер.
Диагностические метаданные объясняют, была ли цель отфильтрована, не выбрана или
опущена бюджетом; они не заменяют фактические результаты и задержку обычного
прохода. Сохраняйте quality misses в отчёте, а не подгоняйте ожидаемые refs под
наблюдаемую выдачу. Успешный выход процесса, в частности, не означает, что найдена
каждая полезная запись. Широкий `crowded-lexical` имеет много допустимых лексических
совпадений: пропуск назначенной цели измеряет ограниченную обнаружимость,
а не доказывает ошибку ранжирования или нерелевантность остальных результатов.

По умолчанию runner завершает работу с кодом 0, если прошли harness и проверки
инвариантов, отдельно сообщая `quality_misses` как число пар набор/случай с
невыполненными ожиданиями, а не число пропущенных записей. Ошибки выполнения
или инвариантов дают ненулевой код. `--fail-on-miss` делает измеренные quality
misses дополнительной причиной ненулевого выхода. Параметр не добавляет порог
времени и не меняет ожидания.

Время включает запуск процесса, работу CLI и захват stdout. JSON parsing,
валидация, генерация корпуса и seed находятся вне таймера. Отчёт хранит первый
вызов отдельно, отдельные повторы, их медиану и p95 методом nearest rank. При
трёх повторах по умолчанию p95 равен максимуму и не оценивает надёжный хвост
задержки. Сохраняйте число повторов; не называйте первый вызов измерением
холодного кеша. Новый процесс не очищает кеши файловой системы или SQLite.
Задержка описательная, а не абсолютный CI-порог прохождения. Время punisher
включает проверку целостности всей базы, даже когда findings обслуживания
строго ограничены проектом.

Для воспроизводимости отчёт фиксирует хеши фикстуры и сгенерированного корпуса,
хеши установленных модулей, версии Python/platform/SQLite, фактические
диагностические счётчики и статистику хранения записей, истории и текущих summary.
Он также проверяет полные целевые записи, происхождение источников, состояния,
бюджеты вывода и неизменность байтовых хешей базы и каждого непустого WAL.
Отсутствующий и нулевой WAL эквивалентны; временный SHM исключён. Reader статистики
явно закрывается перед последующими CLI-чтениями и финальным сравнением.
Эти проверки отличают корректное измерение от присутствия полезной записи
в ограниченном результате.

Каждый сценарий использует временное синтетическое хранилище с явными временными
конфигурацией и home, без унаследованных `RICHI_*`, `PYTHON*` и `CODEX_THREAD_ID`.
Изоляция ограничена тестовыми подпроцессами; runtime пользователя, привязка чата
и workspace не переключаются. Production-память, частные корпуса и содержимое
источников не читаются; вымышленные источники не загружаются. Runner измеряет
существующее поведение: не реализует архивацию/очистку и не меняет production retrieval.

См. [MEMORY_GROWTH.md](../docs/MEMORY_GROWTH.ru.md): сохранённый полный запуск,
окружение, измерения и ограничения. Синтетические пропуски и локальная задержка
не устанавливают production-точность, экономию токенов или качество решений агента.

<a id="retrieval-tools-and-storage-growth"></a>
## Инструменты поиска и рост хранения

После установки candidate во временное окружение:

```sh
python evals/evaluate_search_storage.py --output /tmp/richi-search-storage.json
# Optional: a separate Python with tiktoken and cached o200k_base/cl100k_base encodings.
python evals/evaluate_search_storage.py --output /tmp/richi-search-storage-tokens.json \
  --tokenizer-python /path/to/tokenizer-venv/bin/python
```

`TIKTOKEN_CACHE_DIR` может указывать на существующий кеш кодировок. Токенизатор
не является runtime-зависимостью. Если явно запрошенный токенизатор не удаётся
инициализировать, эксперимент завершается до запуска. Без него токены не измеряются.

Runner создаёт только временные синтетические хранилища. Он сравнивает recall
и три отдельных чтения с discover и одним пакетным fetch, проверяет равенство
полных записей и неизменность баз, измеряет локальную задержку чтения в свежем
процессе пятью чередующимися повторами. Follow-up ID выбраны oracle; это не слепая
проверка выбора агента или качества ответа. Токены учитывают только текст
инструментов, без инструкций, reasoning и эффектов биллинга.

Отдельная графовая фикстура проверяет лимит отрендеренного вывода, сохранение
корня и концы рёбер. Фикстура роста сохраняет 100 текущих карточек, добавляет
0, 10 и 100 ревизий метаданных, затем проверяет сохранение всех логических строк,
rowid и результатов recall после явного обслуживания индекса. Физические размеры
разделяют текущий текст, историю, FTS и свободные страницы при поддержке SQLite
`dbstat`. Отчёты содержат хеши runtime-кода и сырого вывода, ограничения покрытия
и отказываются перезаписывать существующий output. Время — наблюдение, не CI-порог;
процессы совместно используют кеши операционной системы.

См. [измеренные результаты 2026-10-23](../docs/RETRIEVAL_STORAGE_EVAL.ru.md), включая
намеренно неполный графовый обзор и отсутствие уменьшения диска после
обслуживания индекса.
